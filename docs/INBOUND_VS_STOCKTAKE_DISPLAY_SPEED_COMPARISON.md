# 入庫と棚卸の処理・表示速度比較と同等化の検討

**目的**: 入庫と棚卸で「同じ規模のデータ」を扱う場合の表示速度の差を整理し、同等にする手段を検討する。

---

## 1. 想定シナリオ

- **10商品グループ / 10配送**、それぞれに **300 SKU** が含まれる場合
- 総 SKU 数: 10 × 300 = **3,000 SKU**

※ 入庫は「配送」単位、棚卸は「商品グループ」単位で選択して表示する前提。

---

## 2. 入庫（Inbound）の処理の流れ

### 2.1 データの持ち方

- **Transfer** → 複数 **Shipment（配送）** → 各配送に **lineItems（明細）**
- ユーザーは「1配送」を選ぶと、その配送の明細だけを表示する。

### 2.2 1配送選択時の読み込み（300 SKU の配送を選んだ場合）

| 処理 | 内容 | 回数・時間の目安 |
|------|------|------------------|
| 1. 配送明細の取得 | `inventoryShipment(id).lineItems(first: 250)` を **1回の GraphQL** で実行 | **1回**（初回は最大250件） |
| 2. 在庫クエリ | 不要（予定数・受入数は lineItems に含まれる） | **0回** |
| 3. 追加読み込み | 250件超ある場合は「読込」ボタンで `after: endCursor` で次ページ取得 | 50件なら 1回追加 |

**合計**: 初回表示まで **GraphQL 1回** ＋ 必要なら監査用の readInboundAuditLog 等。在庫用の N 回クエリは発生しない。

### 2.3 10配送ある場合の体感

- ユーザーは「1配送ずつ」選んで作業する。
- 1回の操作で負荷がかかるのは「選んだ1配送の 250 件（または読込で 300 件）」のみ。
- **表示速度**: 1回の API で明細が揃うため、**速い**。

---

## 3. 棚卸（Stocktake）の処理の流れ

### 3.1 データの持ち方

- **棚卸ID（Count）** → 複数 **商品グループ** → 各グループに商品（コレクション or inventoryItemIds）
- 表示モード:
  - **単一グループ**: 1グループを選んでそのグループの商品リストを表示
  - **まとめて表示**: 全グループの商品を一覧で表示

### 3.2 単一グループ選択時（1グループ 300 SKU を選んだ場合）

| 処理 | 内容 | 回数・時間の目安 |
|------|------|------------------|
| 1. 商品マスタ取得 | `fetchProductsByGroups([groupId], ...)` でコレクション or nodes から商品取得。初回は `productFirst`（設定で最大250）まで | 1〜数回（コレクション数・バッチに依存） |
| 2. 在庫フィルタ・表示用在庫 | `filterByInventoryLevel: true` のとき、取得した各商品に対して `getCurrentQuantity(inventoryItemId, locationId)` を実行。**15件ずつバッチで Promise.all** | 250件なら 250/15 ≒ **17バッチ** → 実質 **250回の GraphQL**（15並列×17ラウンド） |
| 3. 追加読み込み | 「さらに読み込む」で 250 件超を取得。その都度同じく在庫クエリが発生 | 50件追加なら同様に約50回の在庫クエリ |

**合計**: 初回表示まで **商品取得 1〜数回** ＋ **在庫クエリ 約250回（15並列）**。  
Shopify の仕様で「在庫は inventoryItem ごとに1クエリ」のため、**入庫よりどうしても多くなる**。

### 3.3 まとめて表示時（10グループ・合計 3,000 SKU の場合）

- 初回は **全グループから最大 250 件** までを `productFirst` で取得（設定の initialLimit）。
- 250 件分に対して同じく在庫を 15 件バッチで取得 → **約250回の在庫クエリ**。
- 残り 2,750 件は「さらに読み込む」またはグループごとの「読込」で追加取得し、その都度在庫クエリが発生。

**差がつくポイント**: 入庫は「1配送＝1回の API で明細＋数量まで取得」に対し、棚卸は「商品リスト取得」と「在庫取得」が別で、在庫が **SKU 数に比例して N 回** になること。

---

## 4. 表示速度の差の目安（10グループ/10配送・各300SKU）

| 観点 | 入庫（1配送選択・300SKU） | 棚卸（1グループ選択・300SKU） |
|------|---------------------------|-------------------------------|
| 初回表示までの GraphQL 回数 | **1回**（lineItems 250件） | 商品取得 1〜数回 ＋ **在庫 約250回**（15並列） |
| 在庫用の追加クエリ | **0回** | **約250回**（250件表示時） |
| 体感 | 速い（1リクエストで完了） | 遅くなりやすい（在庫の並列でも 250 回分の往復） |

**おおよその差**:  
- 入庫: 1回の API 応答時間（例: 数百 ms 〜 2秒程度）で表示完了。  
- 棚卸: 商品取得に加え、在庫を 15 件ずつ並列で 17 ラウンド → ネットワークと API レート次第で **数秒〜十数秒** になる可能性がある。

※ 実際の値はネットワーク・Shopify API の応答速度・設定（initialLimit など）に依存します。

---

## 5. 同等化のための手段（検討案）

### 5.1 棚卸側で「入庫に近づける」施策

| 施策 | 内容 | 効果・注意 |
|------|------|------------|
| **初回表示件数を揃える** | 入庫は実質 250 件で初回。棚卸も `productList.initialLimit` を 250 に統一済み。さらに「初回は件数のみ表示し、在庫は遅延読み込み」にするなど、入庫のように「まず一覧を出してから在庫を後付け」にする | 体感が入庫に近づく。実装コストは中。 |
| **在庫クエリのバッチ拡大** | 現在 15 件バッチ。レート制限に注意しつつ 20〜25 件などに増やす | ラウンド数が減り、やや短縮。効果は限定的。 |
| **在庫なしはスキップ** | 「在庫レベルでフィルタ」をオプションにし、フィルタなしなら在庫クエリを飛ばして一覧だけ先に表示。在庫は「在庫更新」ボタンやスクロール時に取得 | 初回表示は入庫並みに速くなる。在庫表示は後からになる。 |
| **一覧用は在庫を取らない** | 棚卸一覧（InventoryCountConditions）の「未完了グループの数量」表示で、在庫を取らず件数のみ表示する（既に一部で件数のみの表示がある場合はその拡張） | 一覧表示の体感が軽くなる。 |

### 5.2 入庫側で「棚卸に揃える」必要はあるか

- 入庫は **Shipment API が明細と数量を一括で返す** ため、元々 N+1 が発生しない設計。
- 無理に「入庫も在庫を1件ずつ取る」ようにすると遅くなるだけなので、**入庫は現状のまま**でよい。

### 5.3 推奨の方向性

1. **表示速度の「同等」** = 「初回表示が遅くならない」ことに置くなら、  
   - **棚卸の初回は「商品リストのみ」先に出し、在庫数はバックグラウンドまたは「在庫更新」で取得する**方式が有効。
2. **現状維持で揃える**なら、  
   - 初回表示件数（250）を入庫・棚卸で統一済みなので、**棚卸の在庫クエリを 15 件バッチのままでも、レート制限内でバッチ数を増やす**程度で差を少しだけ縮められる。
3. **ドキュメント・設定で揃える**なら、  
   - 「棚卸は在庫を商品ごとに取得するため、商品数が多いと入庫より時間がかかることがあります」と設定画面やヘルプに明記し、必要なら initialLimit を下げる（例: 100）ことで体感を軽くする。

## 6. まとめ

| 項目 | 入庫 | 棚卸（改善後） |
|------|------|----------------|
| 1配送/1グループ 300 SKU の初回表示 | **1回の GraphQL** で明細＋数量まで取得 | **商品取得のみ**（在庫は「在庫更新」で取得） |
| 表示速度の差 | 速い | **入庫に近い**（初回は在庫クエリなし） |
| 同等化のポイント | 変更不要 | ✅ 履歴一覧・商品リストで在庫クエリを遅延／省略（下記「7. 実装した改善」参照） |

**10商品グループ/10配送・各300SKU** のときは、**1配送・1グループ** ごとに見ると、  
- **入庫**: 1回の API で 250 件表示。  
- **棚卸（改善後）**: 初回は商品マスタのみ取得で 1〜数回の GraphQL。在庫数は「在庫更新」ボタンで 15 件ずつバッチ取得。

---

## 7. 実装した改善（入庫の処理速度に近づける）

アプリタイルの **履歴一覧・グループ一覧・商品リスト** の 3 レベルで、以下の変更を実施した。

| レベル | 改善内容 | 変更ファイル |
|--------|----------|--------------|
| **履歴一覧** | 未完了グループの在庫数を**自動取得しない**。一覧表示は軽量データのみ（入庫の履歴一覧と同様に追加クエリなし）。数量は groupItems がある場合のみ表示、未取得時は「—」。 | `InventoryCountConditions.jsx`：`loadIncompleteGroupQuantities` の useEffect を削除 |
| **グループ一覧** | もともと在庫数は「在庫数読込」ボタンで取得しており自動読込なし。商品グループ名は `getProductGroupName` の 60 秒キャッシュで軽量化済み。 | 変更なし |
| **商品リスト** | 初回表示・「さらに読み込む」とも **在庫クエリなし**（`filterByInventoryLevel: false`）。在庫数は「在庫更新」ボタンで取得。在庫更新時は 15 件ずつバッチでレート制限を回避。 | `InventoryCountList.jsx`：初回・追加読み込みで `filterByInventoryLevel: false`、在庫更新を 15 件バッチに変更 |

これにより、棚卸の **履歴一覧の表示** と **商品リストの初回表示** が入庫に近い速度になり、在庫数が必要なときだけ「在庫更新」で取得する運用になる。

---

## 8. 現在の実装での処理速度の目安（入庫 vs 棚卸）

※ いずれも「1配送／1棚卸・1グループ・約250件」を想定。実際はネットワーク・API応答に依存します。

| 局面 | 入庫 | 棚卸（現在の実装） | 差の目安 |
|------|------|---------------------|----------|
| **履歴一覧が表示されるまで** | GraphQL **1回**（transfers 一覧＋数量含む） | 軽量メタフィールド **1〜数回**（在庫クエリなし） | **ほぼ同等**（〜2秒程度） |
| **商品リストが表示されるまで** | GraphQL **1回**（lineItems 250件・数量含む） | 商品取得 **1〜数回**（在庫はバックグラウンド） | **ほぼ同等**（リストだけなら 1〜3秒程度） |
| **商品リストで在庫まで全部揃うまで** | 上記1回で **完了**（〜2秒） | リスト表示後、在庫を **15件ずつバッチ**（250件なら約17ラウンド）でバックグラウンド取得 | 棚卸は **在庫が埋まるまで十数秒** かかる可能性あり（操作はブロックされずスキャン・カウント可能） |

**まとめ**

- **「一覧・リストが表示される速度」**は、現在の実装で **入庫と棚卸はほぼ同等**。
- **「在庫数まで含めてすべて揃うまでの時間」**は、入庫は 1 回の API で完了するのに対し、棚卸は在庫が **バックグラウンドで順に埋まる** ため、全件揃うまでには **数秒〜十数秒** かかることがある。その間もスキャン・カウントは可能。
