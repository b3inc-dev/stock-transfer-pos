# 管理画面・棚卸：複数ブラウザ同時利用時の負荷

**質問**: 10以上など複数ブラウザで、30グループ以上・5000 SKU の棚卸IDの画面を全てのブラウザで開くと、全ての処理が遅くなるか。

**結論**: **はい。現在の設計だと、複数ブラウザで重い棚卸画面を同時に開くと、全体が遅くなりやすいです。**

---

## 1. 負荷がかかるのはどこか

| 処理 | いつ実行される | 重さの要因 |
|------|----------------|------------|
| **Loader** | 各ブラウザで棚卸ページを開いたとき（初回・リロード） | メタフィールド読み取り（list またはフルチャンク）、商品グループ、設定、ロケーション。Shopify GraphQL を数回〜数十回。 |
| **get_count_full** | モーダルを開いたとき（groupItems がない棚卸のみ） | `readInventoryCountsChunked(admin)` で全チャンクを取得。Shopify へのリクエストが増える。 |
| **get_incomplete_group_products** | モーダルを開いたとき（未完了グループごとに 1 リクエスト） | **1 グループあたり最大 600 SKU** を、**5 件ずつバッチ**で GraphQL（商品＋在庫）。バッチ間に 180ms 待機。30 グループなら **30 回の action**。 |

---

## 2. なぜ「全て遅く」なりやすいか

### 2.1 サーバー（Node）の処理能力

- 各ブラウザからの **action**（get_incomplete_group_products / get_count_full）は **同じ 1 台のアプリサーバー**に飛ぶ。
- 1 回の get_incomplete_group_products は「多数の Shopify GraphQL 呼び出し ＋ 180ms 待機」で **数秒〜十数秒** かかる。
- 10 ブラウザが同時にモーダルを開くと、**10 × 30 = 300 本**の get_incomplete_group_products が短時間に並ぶ。
- Node は 1 プロセスあたり 1 スレッドでリクエストを処理するため、**リクエストがキューに溜まり、どのブラウザも待たされやすくなる**。

### 2.2 Shopify API のレート制限

- 同一ショップの管理画面は、**同じ Shopify Admin API のレート制限**を共有する。
- 10 ブラウザ × 30 グループ ×（グループあたり数百回の GraphQL）＝ **数万リクエスト**が短時間に集中する想定。
- **Throttled / 429** が増え、リトライや待機が増えるため、**全ブラウザで応答が遅くなる**。

### 2.3 ブラウザ間でキャッシュを共有しない

- 各ブラウザは独自に「モーダルを開く → get_incomplete_group_products を 30 回」を発行する。
- サーバー側に「同じ countId + groupId の結果をキャッシュして使い回す」仕組みはないため、**同じ棚卸を 10 タブで開けば、同じ取得が 10 倍繰り返される**。

## 3. 目安（30 グループ・5000 SKU の棚卸）

| 同時ブラウザ数 | 想定 |
|----------------|------|
| **1** | モーダルを開くと 30 回の get_incomplete_group_products が順次実行。1 グループあたり数秒〜十数秒なら、全体で数十秒〜数分かかる可能性。 |
| **10 以上** | 上記が 10 倍以上のリクエスト数になる。サーバーキューと Shopify のスロットリングで、**どのブラウザも遅くなりやすい**。 |

---

## 4. 緩和の方向性（参考）と実装済み対策

### 4.1 実装済み：サーバー側キャッシュ（同一ショップ複数ブラウザ対策）

- **get_incomplete_group_products** のレスポンスを、**ショップ・棚卸ID・グループID・offset** をキーに **2 分間** メモリキャッシュするようにした。
- 同じ棚卸の同じグループを 2 回目以降に開いたとき（別タブ・別ブラウザ含む）は、**Shopify API を叩かずキャッシュを返す**ため、複数ブラウザで同時にモーダルを開いても、先に取得した結果を共有でき、負荷が軽減される。
- 棚卸の内容が変わったときに古いキャッシュを返さないよう、**数量更新・グループ確定・リセット・キャンセル** の各 action 成功時に、その棚卸ID用のキャッシュを無効化している。
- **注意**: キャッシュは **1 プロセス内のメモリ** のため、**複数インスタンス（レプリカ）で動かしている場合はインスタンスごとにキャッシュ** になる。Redis 等で共有すれば、さらに複数ブラウザでの効果が大きくなる。

### 4.2 その他の緩和案（未実装）

- **同時実行の制限**: 同一ショップで「get_incomplete_group_products の同時実行本数」に上限を設ける（キューやセマフォで制御）。
- **モーダルを開くたびに全グループ読まない**: 未完了グループが 30 ある場合でも「表示中のグループだけ」先に取得し、他はスクロールやタブで表示時に取得する。
- **運用**: 重い棚卸（30 グループ・5000 SKU）を開くブラウザ数を減らす、または「モーダルを開く」操作を同時に集中させない。

## 5. 「同じショップ」と「複数アカウント（複数ショップ）」の違い

### 同じショップアカウントで発生する

- **同じショップ**（1 つのストア）で、複数ブラウザ・複数タブ・複数スタッフが同時に管理画面を開き、重い棚卸のモーダルを開くと、そこで説明した「全体が遅くなる」現象が起きやすいです。
- 理由:
  - **Shopify API のレート制限はショップ単位**。同一ショップの全セッションが 1 つの制限を共有するため、同じ店舗の複数ブラウザが一斉に GraphQL を叩くと、そのショップ用の枠がすぐ埋まる。
  - アプリサーバーも、同一ショップからの大量リクエストが短時間に集中するため、キューが溜まりやすい。

### 複数アカウント（複数ショップ）が同時に処理する場合

- **販売時などで、複数ショップ（別々のストア）が同時に処理している**場合は、**同じ問題は基本的に起きません**。
- 理由:
  - **ショップごとに API のレート制限が別**。ショップ A とショップ B は別枠なので、A が重くても B の制限には影響しない。
  - アプリサーバーは両方のリクエストを扱うが、負荷は「ショップごとに分散」した形になり、**1 ショップに 10 ブラウザが集中**するほどにはならない typical な使い方なら、サーバー負荷もレート制限も問題になりにくい。

まとめ:

| 状況 | レート制限 | サーバー負荷 | 問題の出やすさ |
|------|------------|--------------|----------------|
| **同一ショップ**で複数ブラウザが重い棚卸モーダルを同時に開く | 1 ショップの枠を全員で共有 → すぐ枯渇しやすい | 同一ショップからのリクエストが集中 → キューが溜まりやすい | **遅くなりやすい** |
| **複数ショップ**がそれぞれ販売・棚卸などを同時に処理 | ショップごとに別枠 → 互いに干渉しない | ショップごとに分散 → 集中しにくい | **通常は問題になりにくい** |

※ 同一ショップ内の「複数スタッフアカウント」は、同じ 1 ショップとして扱われるため、上記の「同じショップアカウント」のケースになります。
