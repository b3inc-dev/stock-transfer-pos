# POS 棚卸明細リスト パフォーマンス最適化 — 要件定義

Phase 5 パフォーマンス監査に基づく「大きなリストで Pagination / VirtualList 未使用」対応の、**最適解の要件**をまとめたドキュメントです。

---

## 1. 目的・背景

### 1.1 課題

- **extensions/stock-transfer-stocktake/.../InventoryCountList.jsx** で、棚卸明細（`lines` / `groupLines`）を **.map で全件 DOM 描画**している。
- 行数が **数百〜数千** になると、以下が発生しうる：
  - 初回描画・スクロールの体感が重い
  - メモリ使用量の増加
  - POS 端末（タブレット等）でカクつきが目立つ

### 1.2 目標

- 大量明細でも **体感速度・操作性を維持**する。
- **POS UI Extension の制約**（利用可能コンポーネント・API）を満たす。
- 既存の「**さらに読み込む**」による追加取得と **矛盾しない**設計にする。

---

## 2. 制約（POS UI Extension）

### 2.1 技術スタック

- **@shopify/ui-extensions**: 2025.10.x
- **Preact** + **s-*** 系コンポーネント（s-box, s-stack, s-text, s-button 等）
- 拡張ターゲット: POS 画面（モーダル・タイル等）

### 2.2 利用可能な UI 要素（POS UI Extensions ドキュメントより）

| 種別 | 内容 | 備考 |
|------|------|------|
| **ScrollView** | スクロール可能コンテナ | プルリフレッシュ・スクロール位置コールバック・遅延読み込みに適したレンダリング |
| **List** | 構造化データの行表示 | **ページネーション対応**（`isLoadingMore`、末尾到達コールバック等） |
| **s-stack / s-box** | レイアウト | 現状の棚卸明細リストで使用中 |

- **VirtualList** に相当する「表示域だけ DOM 化する」公式コンポーネントが **POS 向けに明示されているかは要確認**（通常の Web 用 react-window 等は POS 拡張では利用不可の想定）。
- **List** は「Paginated data」を前提としており、**末尾到達時に追加読み込み**するパターンと相性が良い。

### 2.3 既存の「さらに読み込む」との関係

- 現在、**商品リスト**は **fetchProductsByGroups** / **searchVariants** 等で **ページング取得**（first/after）しており、**「さらに読み込む」**で次のページを追加している。
- つまり「**データの追加読み込み**」は既にある。「**表示側で何件ずつ見せるか**」を制御する **ウィンドウリング or ページ切り替え**が未実装。

---

## 3. 選択肢の比較

| 方式 | 説明 | メリット | デメリット |
|------|------|----------|------------|
| **A. VirtualList（ウィンドウリング）** | 表示域付近の行だけ DOM に描画し、スクロールに応じて描画範囲をスライドさせる。 | 大量件数でも DOM 数が少なく軽い。スクロールで全件を「なめらかに」閲覧できる。 | POS の公式コンポーネントに VirtualList が無い場合、自前実装（スクロール位置・高さ推定）が必要で実装コストが高い。 |
| **B. ページネーション（N 件ずつ表示）** | 例: 50 件ずつ表示し、「次へ」「前へ」でページ切り替え。 | 実装が明確。DOM 数が常に N 件で抑えられる。List の「追加読み込み」と組み合わせやすい。 | ユーザーが「次の 50 件」に遷移する操作が 1 回増える。 |
| **C. 現状の「さらに読み込む」のみ強化** | 全件 DOM のまま、**初回表示件数**だけ 50 件などに制限し、残りは「さらに読み込む」で追加。 | 変更範囲が小さい。 | 一度「さらに読み込む」を繰り返すと、結局 DOM が増え、重くなりうる。 |

---

## 4. 最適解の要件（推奨）

### 4.1 推奨方針: **「表示ページネーション」+ 既存の「データ追加読み込み」の併用**

- **表示側**: いま持っている **lines**（または group ごとの groupLines）のうち、**N 件ずつ**だけ DOM に出す（例: **50 件 / ページ**）。
- **データ側**: これまでどおり「**さらに読み込む**」で API から次のページを取得し、**lines** に追加する。
- つまり「**1 ページあたりの表示件数**」を固定し、**ページ切り替え**で同じデータの別範囲を見せる。必要なら「**さらに読み込む**」でデータを増やしてから、次の表示ページに進む。

この組み合わせが、**POS の List / ScrollView の仕様**と、**既存の fetch 設計**の両方と矛盾せず、実装コストと効果のバランスが良いと判断する。

### 4.2 機能要件

| ID | 要件 | 詳細 |
|----|------|------|
| F1 | **1 ページあたりの表示件数** | 初期値 **50 件**（設定で変更可能にする場合は 25 / 50 / 100 等）。 |
| F2 | **ページ切り替え UI** | 「前へ」「次へ」、および可能なら「1, 2, 3 … 最後」のようなページ番号（POS の画面幅に収まる範囲で簡易版で可）。 |
| F3 | **件数・位置の表示** | 例:「51–100 件目 / 全 320 件」のように、現在の表示範囲と総件数を表示する。 |
| F4 | **単一グループ / 複数グループ** | 複数グループ時は **グループごとのリスト** に対してページネーションを適用する（グループ単位で「50 件ずつ」等）。単一グループ時は **lines** を 50 件ずつ表示。 |
| F5 | **「さらに読み込む」との関係** | 現在の「さらに読み込む」は **データの追加取得**として維持。表示上は「全データの 1 ページ目〜M ページ目」のうち、現在ページの N 件だけを描画する。 |
| F6 | **予定外リスト** | 予定外リスト（extraLines）も同様に **N 件ずつ表示**するか、件数が少ない場合は全件表示とする（仕様でどちらにするか決定）。 |

### 4.3 非機能要件

| ID | 要件 | 詳細 |
|----|------|------|
| NF1 | **POS 対応** | @shopify/ui-extensions 2025.10.x および利用可能な **List / ScrollView / s-*** のみで実装する。 |
| NF2 | **既存挙動の維持** | 既存の「確定」「リセット」「実数入力」等の動作は変えない。行の key は **inventoryItemId** や **variantId** 等の安定 ID を維持する。 |
| NF3 | **アクセシビリティ** | ページ切り替えはタップ／キーボードで操作可能にする（POS の標準操作に合わせる）。 |
| NF4 | **パフォーマンス** | 1 画面あたりの描画行数は **最大 N 件**（推奨 50）に抑え、それ以上はページ切り替えで表示する。 |

### 4.4 実装時の注意点

- **List** コンポーネントが「末尾到達でコールバック」を持つ場合、そのコールバックでは「**次のデータ取得**」（さらに読み込む）と「**次の表示ページへ**」のどちらを発火させるか役割を分ける（例: 表示は 50 件固定でページ切り替え、データは「さらに読み込む」ボタンで追加）。
- **ScrollView** 内に「現在ページの N 件」だけを置き、ページ切り替えで中身の配列を **slice((page-1)*N, page*N)** に差し替える、という形でもよい。
- **InventoryCountLineRow** は **memo** でラップし、同一 props の行は再レンダーをスキップする（Phase 5 の別項目と一致）。

## 5. VirtualList を採用する場合の追加要件（オプション）

- POS に **VirtualList** 相当の公式コンポーネントが存在し、かつプロジェクトで利用可能と判断できる場合に限り、以下の要件を検討する。
- **行の高さ**: 固定高さ or 可変高さ（可変の場合は高さ推定 or 実測が必要）。
- **スクロール位置**: ScrollView の onScroll 等で現在位置を取得し、表示すべき「開始インデックス」「終了インデックス」を計算する。
- **バッファ**: 見えていないが直近の行を数件前後に余分に描画し、スクロール時の白抜けを防ぐ。

※ 公式に VirtualList が提供されていない、または実装コストが大きい場合は、**4. のページネーション方式を最適解**とする。

---

## 6. 受け入れ条件（まとめ）

- [ ] 棚卸明細が **100 件以上** ある場合でも、**1 画面に描画する行数が N 件（推奨 50）に制限**されている。
- [ ] 「**前へ」「次へ**」等のページ切り替えで、同じデータの別範囲が表示される。
- [ ] 「**さらに読み込む**」で取得したデータも、表示上は **N 件ずつのページ**で閲覧できる。
- [ ] 単一グループ・複数グループの両方で、上記が成立する（グループごとにページネーションを適用する場合、その仕様を満たしている）。
- [ ] POS UI Extension の **利用可能コンポーネントのみ**で実装されている。
- [ ] 既存の確定・リセット・実数入力・key の付け方に変更がない。
