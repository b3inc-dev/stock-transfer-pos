# 在庫履歴の読取失敗: #46 の途中修正

## 修正範囲

`inventory_levels/update` の直前履歴・代替数量・重複キーの読取に失敗した場合は HTTP 503 を返し、履歴を保存しない。Prisma の履歴モデルが使用できない場合も同じ扱いにする。正常に読取できた結果が0件の場合とは区別する。

合成イベントで、読取の連続失敗時に保存0件、回復後の同一イベント再送で正しい差分1件のみ保存、キーなし履歴を生成しないことを検証する。Shopify実接続、実在庫操作、配備は実施していない。

## 本番反映を止める未解決事項

初期数量10からA(8)を処理中に読取失敗した後、後発B(7)が成功してからAが再送されると、現状はB=-3、A=+1となる。期待する時系列のA=-2、B=-1にはならない。503による再送と組み合わせて発生するため、本修正だけで復旧・順不同の受入合格とはしない。

`tests/inventory-webhook-history-read.test.mjs` の最後の試験はこの条件の正しい期待値を持つ **失敗中のTODO**。成功件数には含めない。永続的な順序管理・照合方針を確定して修正し、TODOを解除して再監査するまでdraftおよび本番不可を維持する。

#53、メタデータ補完の #62、タイムゾーン照会の #63 はそれぞれ別の変更として追跡する。本PRはそれらの統合・受入完了を主張しない。過去に誤保存された履歴の自動修正も含まない。
