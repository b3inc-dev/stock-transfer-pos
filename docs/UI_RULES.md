# 管理画面の UI ルール（完全版 v1.1）

> 正本は T の Doc（https://claude.ai/artifact/HJKZiW8SdoG5aV2MphsFDj）、この写しは v1.1（2026/11/22）。写しと正本が違うときは正本に合わせ、この写しを直す。

2026/11/22 · T

> このアプリでの読み方（T、2026/11/22）: ルールの文と Shop Point の今の実装（`staging` の `app/components/admin-ui.tsx` と各画面）が違うときは、Shop Point の今の実装に合わせる。見た目・部品・CSS は Shop Point をお手本にする。

Shop Point の管理画面で実装し、T さんが検証と本番で確かめた決まりの完全版です。v1.0 に、11/21〜11/22 の実装（PR #66・#67・#73・#57・#80・#91 ほか）で決まったことと、部品の名前・CSS の注意点を足しました。POS Stock・POS Receipt など、ほかのアプリもこのルールで作ります。前提は Shopify の審査基準（Built for Shopify 4章「デザイン」）を守ることで、そのうえで VIP の管理画面のように短く見やすくします。部品は Shop Point の `app/components/admin-ui.tsx` にあり、ほかのアプリはこのファイルを写して使います（13章）。

## 1. 部品の選び方

- Shopify に部品があるものはそれを使う（Polaris web components の `s-` タグと App Bridge）。自前の見た目を作るのは、上部メニュー・戻るボタン・入力表など Shopify に無いものだけ。
- 色は意味で決める。緑＝有効・完了、青＝これから・処理中、黄＝要確認、赤＝失敗と取り消せない操作、灰＝停止・終了。飾りに色を使わない。
- 画面を作るときは、まず 13章の部品で組む。同じ見た目を画面ごとに書き直さない。

## 2. 画面の形

画面の役割で、3つの形を使い分けます。迷ったら「入力して保存するなら1、1件を見るなら2、並べて見るなら3」です。768px 未満はどの形も縦に1列です。

| 形 | 使う画面 | 例 | 部品 |
|---|---|---|---|
| 1. 左に見出し＋1〜2文の説明、右に白いカード | 入力して保存する設定 | 設定の区分、誕生日、友達招待のルール | `AdminBlock`（既定） |
| 2. カード2列（左に主な内容、右に要約） | 1件を見る詳細とホーム。スマホでは要約が上 | 会員の詳細、ホーム | `.Admin-home` / `-main` / `-side` |
| 3. カード1列、見出しと説明はカードの中 | 幅が要るもの、上から順に読むもの | 一覧、表、履歴、レポート、データの入口、料金プラン | `AdminBlock wide`、`LinkRows` |

| 対象 | 幅 |
|---|---|
| 本文 | 最大 1200px、左右の余白 16px（`.Admin-body`） |
| 形1 | 左の説明 1 : 右のカード 2（左 240px 以上、右 320px 以上） |
| 形2 | 右の要約 280〜360px、左は残り全部 |
| 形3 | 本文の幅いっぱい |
| 表の数値・金額・日付・操作の列 | 中身の幅、折り返さない。数値と金額は右寄せ |
| 表の名前・説明の列 | 残りの幅（8文字以上） |

- 設定は「1行の要約＋編集」の一覧（`SummaryRows`）に並べ、入力は1区分だけの編集画面で行う（親の URL の下、左上に「←」）。1枚の大きなフォームにしない。入力が5つを超えるときは見出しのあるカードに分ける。
- 画面全体の説明が要るときだけ、本文の上に `AdminIntro` を置く（1〜2文）。

## 3. メニューと移動

- Shopify の左のアプリメニュー（`s-app-nav`）を必ず使う。編集画面でも親の項目を選択中にする。
- 本文上部のメニュー（`AppNavBarView`）は VIP 風で、選択中は灰色の角丸の背景（#e3e3e3）で強調する。親の下の編集画面（例 `/app/earn-rules/earn`）でも親を選択中にする（`match`）。PC は折り返し、スマホは1行の横スライドで、選択中の項目が見える位置まで自動で送る。公開版の審査では外すことがある。
- 公開版だけの項目（「料金プラン」など）は公開版のサーバーで、自社用でない店にだけ出す。自社用（Ciara）の画面には出さない。
- ページ内タブ（`SectionTabs`）は同じ画面の中身を切り替えるときだけ使う（例: 移行の取り込み元「メタフィールド・タグ／CSV」）。項目ごと・ランクごとにタブを分けない。どの幅でも1行の横スライドにし、選んだタブは太字と青い下線。太字の幅は `::after` で先に取ってあるので隣がずれない。
- 下の階層の画面には `BackAction` を置く。s-page の直下、`.Admin-body` の前に書く。
  - アプリの画面の中の左上に「←」だけの枠なしボタン（32px 角、触れたときだけ灰色の角丸）を出す。
  - `s-link slot="breadcrumb-actions"` は Shopify の上の帯に文字で出るだけで、アプリの画面の中には何も出ない。breadcrumb だけで戻るボタンの代わりにしない（PR #73）。帯の文字は戻り先の画面名にする（`label` の「◯◯へ戻る」から「へ戻る」を外して使う）。
  - 新しい下の階層の画面は `tests/back-action-coverage.test.mjs` の `SUB_PAGES` に足し、付け忘れを試験で止める。条件で下の階層になる画面（履歴で会員を選んだとき）も同じ。
- 下の画面へ移る行は、行全体を押せるようにして右端に「›」を付ける（`LinkRows`）。

## 4. ボタンとリンク

- リンクに下線を付けない。「編集」などの操作はボタンにする。ページ下部に文字だけのリンクを置かない（`AdminFooterLinks`・`.Admin-text-link` は新しい画面で使わない）。メニューから行けない画面へは、タイトル＋カードの中のボタンで移る（例: 移行画面の「次の手順」カード）。
- 画面内の移動は `GuardedLink` 系（`PrimaryLink`・`SecondaryLink`・`LinkRows`）を使う。未保存の入力があるとき、移る前に Shopify の確認を出す。
- ボタンは Shopify と同じ大きさ（高さ 28px、スマホ 40px）。ボタンだけの行を作らず、見出しの右・説明の下（`AdminBlock` の `action`）・行の右端に置く。
- ボタンの文字は「動詞」か「名詞＋動詞」で短くする（保存、施策を追加、書き出す、続きから再開）。

| 種類 | 使う場面 | 部品 |
|---|---|---|
| 主ボタン（黒） | 画面の一番の操作。1画面に1つ（「施策を追加」「ランクを追加」） | `PrimaryLink`、`PrimaryButton`、`.Admin-primary` |
| 白いボタン | ふつうの操作（行の「編集」、「商品を選ぶ」「書き出す」「依頼を処理」） | `SecondaryLink`（表の中は `small`）、`.Admin-secondary` |
| 枠なしボタン | 控えめな操作（やめる、もっと見る、「←」） | `.Admin-tertiary`、`BackAction` |
| 赤いボタン | 取り消せない操作だけ。確認の窓の中にだけ置く（「削除」「付与する」） | `ConfirmAction`（窓の中の `.Admin-critical`） |
| アイコン付きボタン | 追加・書き出し・取り込みだけ | `PrimaryLink icon=` など |
| アイコンだけのボタン | 行の削除（ゴミ箱）、並べ替え（上・下の矢印）、「…」、見出し横の「ⓘ」。触れると名前が出る | `DeleteIconButton`、`MoveIconButton`、`MoreActions`、`ConfirmAction trigger="icon"` |

- 表の行の削除はゴミ箱マークだけにする。1件の編集画面では下に「削除」ボタン。行の操作が3つ以上なら、3つ目からは「…」（`MoreActions`）にまとめる。
- 取り消せない操作は確認の窓（`ConfirmAction`）を出し、何がどうなるかを1文で書く。窓を開くボタンは、削除なら赤、処理を始めるだけなら白（`trigger="secondary"`）。取り消せない入力（誕生日の登録など）も、登録前に窓で確認する。
- 押してから終わるまでは、そのボタンを読み込み中にし（文字を「処理中…」にするか、くるくる）、二重に押せないようにする。
- 手動の加算・減算には、社内用の「理由」とは別に「お客様に表示する名前」（40文字まで）を必須で入力させる。お客様の履歴にはこの名前を出す。

## 5. 状態・お知らせ・文章

- 状態は文字でなくバッジ（`StateBadge`）で出す。言葉はアプリの中で揃え、色は言葉で決まる（`BADGE_TONES`）。

| 言葉 | 色 | 使う場面 |
|---|---|---|
| 有効・適用中・完了・付与済み | 緑 | 動いている、終わった |
| 開始前・受付・処理中・実行中 | 青 | これから、進んでいる |
| 停止中・終了・無効・下書き | 灰 | 止めた、終わった |
| 未設定・要確認・一部失敗 | 黄 | 人が見る必要がある |
| 失敗・エラー | 赤 | 失敗した |

- 長い処理が失敗で止まったときは「停止中」を赤（`tone="critical"`）で出し、お知らせ枠で理由と「続きから再開」を出す（12章）。
- 「未設定」は本当に何も保存していないときだけ使う。保存済みでまだ始まらないものは「開始前」にし、あと何を保存すれば始まるかを区分の名前で書く（例:「あと「返品のとき」を保存すると、付与と利用が始まります。」。`pendingSectionsText`）。
- お知らせ枠（`StatusBanner`、中は `s-banner`）は1画面に1つまで。重なるときは失敗、注意、案内の順に1つだけ出す。
  - 実装は、画面の上で `notice` を1つだけ決めてから描く（PR #67 の移行ファイル・誕生日の画面の形）。カードの中に `<p role="alert">` を散らして、ページの失敗をいくつも出さない。
  - 見出しは何が起きたか、本文はどうすればいいかを書く。次の画面へ進む操作があるときは、枠の中のボタン（`slot="secondary-actions"`）にする（例: 公開版の「料金プランを見る」）。
  - 欄の誤りは、お知らせ枠とは別に欄の下の赤い文字（`role="alert"`）で出してよい。
- 失敗したときは理由を書く（「入力を確認してください」だけにしない）。どの欄か・どの行かが分かるときは名前を出し、Shopify 側の理由（権限・混雑・IP 制限など）も分けて書く。理由はサーバーの記録にも残す（顧客の値は残さない）。
- 説明は1〜2文。何段落もの説明を画面に出さない。細かい条件は欄の下の薄い文字（`.Admin-note`）に1文で書く。欄の名前は、それだけで意味が分かる言葉にする。
- まだ何もない一覧は空の表示（`EmptyState`: 見出し＋1文＋最初の操作のボタン）。絞り込みの結果が空のときは文字だけにする。
- 店の人を不安にさせるだけの数字（ホームの「保留」「取消」の件数など）は出さない。対応が要るものだけを出す。

## 6. 入力

- 単位は欄の中の右端に出す（円以上・%・pt・日。`UnitInput`）。補足は欄の下の薄い文字にし、見出しの括弧に説明を詰めない。
- 選択肢が2〜5個ならラジオ、6個以上ならプルダウン。保存して効くものはチェックボックス。
- 多くの中から選ぶもの（商品・店舗・顧客）は、Shopify の選択画面か、検索付きの選択リスト（`PickList`。7件以上で絞り込み欄、上に「すべて」の行）にする。ID の手入力は読み取りに失敗したときだけ。
- 同じ項目を並べて決めるもの（ランク・誕生月の定額など）は、1行1件の入力表（`EditTable` / `EditRow` / `EditCell`）にする。スマホでは見出しを隠し、欄ごとに見出しの付いたカードになる。
- 行の順は人が並べた順のまま保存し（並び順の列を持つ）、名前順などに勝手に並べ替えない。別の画面に同じ一覧を出すときも同じ順にする（誕生日の表はランクの画面と同じ順）。並べ替えは行の矢印（`MoveIconButton`）で行う。
- まだ1件も保存していなくても、判定に使う欄（ランクの判定の基準など）は出し、入れた値を落とさない。
- 日付欄は枠からはみ出さないようにする（iPhone Safari も。13章の CSS）。
- 通知先のメールなど、取り込みごとに違うものは毎回入力にし、初期値を入れない。

## 7. 保存

- 保存は Shopify の保存の帯（`SaveBar`、App Bridge の `SaveBar`）を使う。値が保存したときと違うときだけ上部に「破棄」「保存」を出し、画面の中に保存ボタンを置かない。
- 帯は一度に1つしか出せないので、一緒に決める値は1つのフォームにまとめ、1回の保存で全部を保存する。行ごとに別々のフォームにしない。1画面の `SaveBar` は1つ（誕生日の画面は試験で確かめている）。
- 保存の前に全部の入力を確かめ、1つでも誤りがあれば何も保存しない（1つの取引で保存する）。途中まで保存された状態を作らない。どうしても段階に分かれるときは、どこまで保存したかを画面で知らせる。
- 入力を黙って捨てない。画面に出ていない欄の値が来たとき、受け取れない値が来たときは保存を断り、理由を出す。
- 成功はトーストで出し、保存のたびに出す（同じ文でも出す）。失敗は消えるトーストにせず、画面の赤いお知らせと欄の下の赤い文字に残す。失敗したあとは帯をもう一度出し、そのまま保存し直せるようにする。
- 未保存のまま別の画面へ移るときは、Shopify の確認を出す（`GuardedLink` が行う）。

実装の決まり（PR #66 で直した「何回か押さないと保存されない」「2回目にトーストが出ない」の再発防止）:

- `SaveBar` はフォームの中に置く。開いた時点・保存した時点のフォームの値（`formSnapshot`）を基準にし、今の値が基準と違うときだけ帯を出す。遅れて届く change や部品の作り直しで帯を出し直さない。
- 保存に失敗したら `failed` を渡す。送る前の値と比べ直して帯を出し直す。
- React の状態で持つ入力（ランク表・選んだ商品など）は、「破棄」で `onDiscard` から元に戻す。JS で欄を書き換えたら `markFormDirty` で知らせる。
- 絞り込みの欄など保存しない入力は `data-not-form-value` を付け、帯を出さない。
- 保存以外の成功は `SuccessToast` で出し、`trigger` に結果そのものを渡す（同じ文でも毎回出る）。

## 8. 一覧と表

- 表はカードからはみ出さず、列が1〜3文字ずつ折り返さないようにする。固定の最小幅は付けず、幅は中身で決める（右端が切れたため外した）。
- 表は `History-table`（必要なら `History-scroll` で囲む）を使い、各セルに `data-label` を付ける。スマホは横スクロールさせず、1件1枚のカードにする（見出しは `data-label` で各行の左に出る）。
- 件数の多い表は、スマホで1件を2〜3行に詰める（`data-report` ごとに grid の位置を決める。例: 1行目に日時と増減、2行目に名前、3行目に補足）。PC の列はそのまま。
- 数値・金額は右寄せ（`History-num`・`Report-break-num`、等幅数字）。状態・ID の列は折り返さない（`History-keep`・`History-id`）。
- 人の一覧は VIP 風の行にする（頭文字の丸、名前とメール、ランクのバッジ、右寄せの数字と下に小さく項目名、右端に「›」）。行全体を押すと詳細へ移る。探す欄1つと、絞り込み・並び替えの選択を上に置く。件数を上に、ページ送り（‹ ›）を下に出す。
- 名前やメールは Shopify から表示のたびに読み、アプリには保存しない。読めないときは顧客 ID で出し、理由を1行書く。
- 履歴（管理画面・お客様アカウントとも）には確定した増減だけを出す。カートの確保とその戻し、保留が動かない行は出さない。
- 形式を揃える。日時は「2026/11/20 18:30」（日本時間）、ポイントは「1,200 pt」、金額は「¥1,200」、空は「—」。

## 9. レポートとグラフ

- 上に数字のタイルを4つまで置き、下に1行の補足を付ける。その下に、指標1つにつきグラフ1枚。
- 軸は1本だけにする（単位の違う値を1枚に重ねない）。推移は線、増えた・減ったは 0 を挟んだ上下の細い棒、内訳は細い横棒と割合で出す。
- 色は青（#2a78d6）と橙（#eb6834）の2色で、赤・緑は使わない。値はホバーの吹き出しで読ませ、全部の数字を書かない。
- 期間の欄（開始日・終了日など）は同じ幅にする。日ごとの細かい表は画面に出さず、書き出し（CSV）に入れる。
- 集計に数秒かかる画面は、画面を先に出し、集計はあとから出す（loader は集計を Promise のまま返し、`Suspense` / `Await` で描く）。待つ間は「集計しています。」の1文（`role="status"`）、失敗は赤いお知らせ「集計できませんでした」にする。画面が固まったように見せない。

## 10. ストアに出さないもの

- 開発・検証・システム確認のための文言と要素（照合のタブ、受付番号、試算、検証用の画面、データ範囲の説明など）は、ストアの管理画面に出さない。検証ストアでしか開けないようにするか、消す（例:「検証会員のメタフィールド同期」は検証環境でだけデータの入口に出す）。
- 文言だけでなく、画面の中身・ボタン・タブも同じ基準で見直す。
- 切替などが終わった店で、もう使わない入口（「VIP からの切替」など）を残すかは T に確認する。

## 11. POS

- POS は POS Stock のロス画面を基準にする。本文全体を標準の余白で囲み、見出し・残高・入力・エラー・ボタンの左右の端を揃える。
- 押してから結果が出るまで、そのボタンを処理中の表示にする。失敗の文は理由が分かる言い方にする（例: ほかのカート・端末で使用中）。

## 12. 長い処理（読み取り・一括付与・移行）

全顧客・全注文を読むような処理は、次の形にそろえます（PR #67 のページ送りの読み取り、誕生月タグの一括付与、#57 の移行）。

- 一括取得（Bulk Operation）に頼らず、ページ送りで少しずつ読み、途中から続けられるようにする。IP 制限などで一括取得が止まる店がある。
- 画面を開いている間は自動で続け（`AutoContinue`）、閉じても裏で毎分少しずつ進むことを説明に1文で書く。
- カードの中に、状態のバッジ（処理中・完了・停止中・要確認）と件数を1行で出す（`role="status"`、数値は右寄せ）。
- 止まったときは、お知らせ枠（5章の1つ）に理由を出し、カードの見出しの下に「続きから再開」を出す。「最初からやり直す」は白いボタンにする。
- 終わったら知らせる通知先のメールは、取り込みごとに入力にする（初期値なし、空欄なら送らない）。
- 結果は件数と合計の「事前確認」のカードで見せてから、次の手順（取り込み・有効化）へ進ませる。この時点では何も変わっていないことを1文で書く。

## 13. 共通の部品と CSS の注意

部品は `app/components/admin-ui.tsx` にまとまっています。ほかのアプリはこのファイルを写し、見た目を画面ごとに書かないでください。

| 部品 | 役割 |
|---|---|
| `AdminStyle` / `adminCss` | 共通の CSS。レイアウトのルートで1回だけ描く |
| `AppNavBarView` | 本文上部のメニュー（選択中の背景、スマホは横スライド） |
| `BackAction` | 下の階層の「←」（画面の中）と上の帯の戻り先 |
| `SectionTabs` / `AdminSections` | ページ内タブ（1行の横スライド） |
| `AdminBlock` / `AdminIntro` | 画面の形1・3、画面全体の説明 |
| `SummaryRows` / `LinkRows` | 要約＋編集の行、下の画面への入口の行 |
| `StatusBanner` / `StateBadge` / `EmptyState` | お知らせ枠、状態のバッジ、空の表示 |
| `ConfirmAction` / `DeleteIconButton` / `MoveIconButton` / `MoreActions` | 確認の窓、行の削除・並べ替え・その他 |
| `EditTable` / `EditRow` / `EditCell` / `UnitInput` / `PickList` | 入力表、単位付きの欄、検索付きの選択リスト |
| `SaveBar` / `markFormDirty` / `SuccessToast` / `LoadingIndicator` | 保存の帯、変更の知らせ、トースト、上端の進捗線 |
| `GuardedLink` / `PrimaryLink` / `SecondaryLink` | 未保存を確かめてから移るボタン型のリンク |
| `EntitlementNotice` | 権限・プラン・利用枠の注意（公開版だけ料金プランへのボタン） |

CSS の注意:

- `adminCss` は `<style>` の文字としてサーバーで描かれ、`"` と `>` が `&quot;` `&gt;` に変わってそのセレクタが効かなくなる。引用符も子セレクタ `>` も書かない。属性は `[aria-pressed=true]` のように引用符なしで書く。
- 日付欄は `appearance: none; min-width: 0; max-width: 100%` と `::-webkit-date-and-time-value { text-align: left }` を付ける（iPhone Safari で枠からはみ出す・中央寄せになるのを防ぐ）。
- スマホ（767px 以下）は、ボタン 40px、入力欄 44px・文字 16px（iPhone で入力時に拡大しない）。タブ・メニューの項目も 44px。
- 形1を縦に積むとき、`flex-basis` が高さになって見出しとカードの間が空くので、`flex: 0 0 auto` にする。
- 横スライド（メニュー・タブ）は `flex-wrap: nowrap; overflow-x: auto` にし、スクロールバーを隠し、選択中を `scrollLeft` で中央へ送る。
- 表は固定の `min-width` を付けない。入りきらない PC の表だけ `History-scroll` で横スクロールさせる。
- リンクは `text-decoration: none`。フォーカスは 2px の青い枠（`outline: 2px solid #2c6ecb`）を残す。

## 14. お客様アカウント（新アカウント画面の拡張）

管理画面とは別の部品の組（Customer Account UI の `s-` 部品）ですが、決まりは次のとおりです。

- セクションの見出しはカードの外に置き、住所など標準のセクションと揃える。
- 関連ページへのボタン（例: 履歴）は、カード内の主要な行の右端に置く。全画面ページには、左上にプロフィールへ戻る「←」を置く。
- 履歴には確定した増減だけを出し（保留やその戻しは出さない）、残高は上から足し算が合うようにする。付与予定は別の表に出す。手動の増減は「お客様に表示する名前」で出す。
- 登録後に変更できない入力（誕生日など）は、確認のモーダルで「登録後は変更できません」と伝える。「お店にお問い合わせください」の文言は出さない。変更できる場合も同じ年に二重に付与しない。
- 設定していない機能の欄は出さない。
- シェアは LINE・X・Facebook・メールとコピー。テーマ側では端末標準の共有メニューを使う。

- [ ] 数秒かかる画面は、画面を先に出して読み込み中を出している
