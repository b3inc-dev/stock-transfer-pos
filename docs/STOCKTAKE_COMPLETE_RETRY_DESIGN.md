# 棚卸確定：待機時間短縮・自動リトライ・再試行UI・APIデータバックアップ

## 1. 目的

- **アプリタイル**: API を送れたら「完了」とみなして待機時間を短縮したい（メタ更新はサーバー側で自動リトライ）。
- **例外以外**: メタフィールド破損など永続的エラー以外は、一定回数まで自動リトライして成功させたい。
- **失敗時**: 対象の棚卸ID・商品グループに「在庫調整は完了、ステータス更新（メタ更新）が必要」と表示し、確定ボタンを「再試行（メタ更新のみ）」に変更。
- **APIデータの保持**: 確定リクエストのペイロードをバックアップし、タイルを閉じた後や管理画面からも「メタ更新のみ」再試行できるようにする。
- **編集不可**: 再試行必要のあいだは商品リストは編集不可とし、メタ更新のみ再試行できるようにする。できる限りシンプルに実装する。

---

## 2. 用語

| 用語 | 意味 |
|------|------|
| 確定API | `POST /api/pos-stocktake-complete`。ペイロードで countId + completedGroups（または groupId + items）を送り、サーバーが read → merge → write でメタを更新する。 |
| メタ更新 | readInventoryCountsChunked → 該当 count をマージ → writeInventoryCountsChunked。 |
| 再試行必要 | 確定API が失敗し、在庫調整・履歴送信は済（または不要）だが、メタのステータス更新が未反映の状態。 |

---

## 3. 全体フロー（案）

### 3.1 タイル側（POS）

1. ユーザーが「確定」を押す。
2. （現状どおり）在庫調整が必要なら `adjustInventoryToActual` → `logInventoryChangeToApi` を実行。
3. **確定API に 1 回 POST**（countId + completedGroups）。
4. **API が ok: true を返したら** → トースト「棚卸を完了しました」、`onAfterConfirm`、下書きクリア。**ここで「完了」とみなす（待機時間＝API 応答まで）。**
5. **API が ok: false かつ needMetafieldRetry: true を返したら**:
   - メッセージ表示:「棚卸ID ○○、商品グループは在庫調整済みです。メタ更新に失敗しました。『再試行』でメタ更新のみ実行してください。」
   - ステータスを「再試行必要」にし、**商品リストは編集不可**にする。
   - 確定ボタンを **「再試行（メタ更新のみ）」** に変更。押下時は同じペイロードで確定API を再送（または retry 専用パラメータで再送）。
6. **再試行ボタンで ok: true が返ったら** → 通常の完了時と同様に扱う（再試行必要を解除）。

「APIを送れたら完了判定」について:
- **案A（同期のまま）**: サーバー側で自動リトライ（2〜3 回）するだけ。成功しやすくなり、失敗時だけ「再試行必要」＋再試行ボタン。クライアントは「API が ok を返すまで待つ」ので、厳密な「送れたら即完了」ではない。
- **案B（非同期）**: 確定API を 202 Accepted で即返し、メタ更新をバックグラウンドで実行。クライアントは 202 で即「完了」表示。失敗時はメタに「再試行必要」を書き、一覧で表示。実装コスト・キュー管理が重い。
- **採用**: まず **案A** で進める（サーバー側リトライ＋失敗時の再試行UI）。体感は「リトライで成功することが増える＝待って成功する」で短縮感がある。案B は必要になったら検討。

### 3.2 サーバー側（api.pos-stocktake-complete）

1. リクエスト受信。認証・body 検証。
2. **受信したペイロードを「バックアップ」に保存**（後述: メタフィールド 1 本で保持）。同じ countId で上書き。
3. **メタ更新を実行**: readInventoryCountsChunked → find count → merge → writeInventoryCountsChunked。
   - **メタフィールド破損系**（例: 「棚卸チャンク○が存在しません」）→ リトライしない。`needMetafieldRetry: true` とエラー内容を返す。
   - **それ以外**（Throttle・一時的なネットエラー・syntax error 等）→ **最大 2〜3 回まで自動リトライ**（間隔は例: 2〜5 秒）。成功したら 200 + `{ ok: true }`。すべて失敗したら 200 + `{ ok: false, error, needMetafieldRetry: true, countId, completedGroupIds? }`。
4. **メタ更新が成功したら** バックアップ用メタを削除（または空で上書き）。

### 3.3 バックアップ（API データの保持）

- **保存場所**: アプリインストールのメタフィールド 1 本（例: namespace `pos_stocktake`, key `pending_complete`）。
- **値**: JSON。例: `{ countId, completedGroups, savedAt (ISO 日時) }`。確定API の body をそのまま保存する（completedGroups または groupId+items を正規化して completedGroups に統一）。
- **保存タイミング**: 確定API のリクエストを受理した直後（メタ更新を始める前）に保存。
- **削除タイミング**: メタ更新が成功したら削除（空オブジェクトや null で上書き）。
- **再試行時の利用**:
  - **タイル**: 同じ count を開いているあいだは、クライアントが持っているペイロードで再送してもよい。タイルを閉じたあとでも再試行できるようにするなら、**再試行時は countId だけ送り、サーバーがメタからバックアップを読んでメタ更新を実行**する方式にするとよい。
  - **管理画面**: 一覧で「再試行必要」の棚卸を表示し、「再試行（メタ更新のみ）」ボタンで、countId だけ（またはバックアップから復元したペイロード）で API または action を呼ぶ。

これで「APIのデータを保持しておく」が実現できる。

### 3.4 管理画面

- 棚卸一覧で、**再試行必要**の棚卸を識別する必要がある。
  - **方法1**: メタの「バックアップ」に countId が存在する ＝ その count は再試行必要の可能性が高い（サーバーが失敗時にバックアップを残すなら、成功時に消すので「バックアップあり＝再試行必要」とみなせる）。
  - **方法2**: 各 count に `needMetafieldRetry?: true` のようなフラグをメタに持たせる。失敗時にその count にフラグを立て、成功時に外す。ただしメタは「全件まとめて」更新しているため、1 件だけフラグを立てるには既存の read → 1 件更新 → write が必要で、やや重い。
- **シンプルな案**: バックアップ用メタに `{ countId, completedGroups, savedAt }` があるとき、「この countId が再試行必要」とみなす。一覧でその count に「メタ更新に失敗しています。再試行してください。」と表示し、**商品リストは編集不可**、「再試行（メタ更新のみ）」ボタンのみ有効にする。
- 再試行ボタン: 管理画面の action で `pos_metafield_retry` のような type を送り、countId を渡す。サーバーはバックアップ用メタからペイロードを読み、同じ read → merge → write を実行。成功したらバックアップを削除し、一覧を再読み込み。

## 4. データ構造（案）

### 4.1 確定API レスポンス（失敗時）

```json
{
  "ok": false,
  "error": "表示用メッセージ",
  "needMetafieldRetry": true,
  "countId": "gid://...",
  "completedGroupIds": ["groupId1", "groupId2"]
}
```

- `completedGroupIds`: 確定リクエストに含まれていたグループIDの一覧。表示用（「このグループは在庫調整済み」と明示するため）。

### 4.2 バックアップ用メタフィールド

- **Namespace**: 既存の棚卸メタと分離するため、例: `pos_stocktake` または既存の `stock_transfer_pos` のサブキー。
- **Key**: 例: `pending_complete`（1 ショップに 1 件のみ。最後に失敗した確定を保持）。
- **Value**: JSON 文字列。
  ```json
  {
    "countId": "gid://...",
    "completedGroups": [ { "groupId": "...", "items": [...] } ],
    "savedAt": "2025-03-04T12:00:00.000Z"
  }
  ```
- 成功時にこのメタを空にする: `{}` または `null` で上書き。

### 4.3 再試行リクエスト（オプション）

- **通常の確定API**: body に countId + completedGroups をそのまま送る（現状どおり）。
- **再試行（メタ更新のみ）**: body に `retryOnly: true` と `countId` だけ送る。サーバーは `countId` でバックアップ用メタを読み、ペイロードを復元して read → merge → write を実行。バックアップが無ければ 400 または 404。

## 5. 実装の優先順位（シンプルに）

1. **サーバー**
   - 確定API 内で read/write を **2〜3 回リトライ**（メタ破損系メッセージのときはリトライしない）。
   - 失敗時に `needMetafieldRetry: true`, `countId`, `completedGroupIds` を返す。
   - 受信ペイロードを **バックアップ用メタに保存**（保存キー・namespace を決める）。成功時にバックアップを削除。
2. **POS タイル**
   - API が `needMetafieldRetry: true` を返したら、メッセージ表示・「再試行必要」状態にし、確定ボタンを「再試行（メタ更新のみ）」に変更。商品リストは編集不可。
   - 再試行時は **同じペイロードを再送**（または `retryOnly: true` + countId でサーバーがバックアップから復元）。
3. **管理画面**
   - 一覧で「バックアップ用メタに countId が存在する」棚卸を「再試行必要」として表示（編集不可＋「再試行（メタ更新のみ）」ボタンのみ）。
   - 再試行 action: countId を渡し、サーバーでバックアップからペイロードを読んでメタ更新のみ実行。

## 6. 注意点（在庫調整・履歴）

- 現状フロー: **確定API が ok を返してから** 在庫調整と履歴送信を行う。**API が失敗した時点では在庫調整・履歴は未送信**。再試行＝メタ更新のみ（在庫調整・履歴は送らない）。在庫調整が必要だった場合に失敗すると、再試行後も実店舗の在庫は未調整のままなので、必要ならユーザーが再度確定フローを行うか運用で対応する。
- **旧文（参考）**: 現状どおり「確定API が ok を返したあと」に在庫調整と履歴送信をしている場合は、**失敗時（再試行必要）には在庫調整・履歴は送らない**。再試行でメタ更新が成功したあと、在庫調整・履歴はすでに送済みかどうかを「再試行必要になった経路」で判定する必要がある。  
  - 実装が簡単なのは「在庫調整なしで確定した場合」の失敗: 再試行はメタ更新のみでよい。「在庫調整あり」の失敗時は、再試行でメタ更新だけ成功させ、在庫調整・履歴は「すでに実行済み」か「未実行」かをクライアントで持っておく必要がある。現在のフローでは「API 成功後にのみ在庫調整・履歴」なので、**失敗時は在庫調整・履歴は未実行**。つまり再試行時は「メタ更新のみ」で正しい（在庫調整・履歴は初回確定時に失敗しているので送られていない。再試行でメタだけ直し、在庫調整・履歴は…… 実は初回で送っていないので、ユーザーが「在庫調整済み」と見なす場合は、再試行後に在庫調整・履歴を別途送る必要がある。ややこしいので、設計では「再試行＝メタ更新のみ」に限定し、在庫調整・履歴は「確定API が ok を返したときだけ送る」現状を維持する。失敗した場合は「メタ更新のみ再試行」でステータスだけ直し、在庫調整・履歴は送られていない状態のまま…… だと不整合になる。  
  - 整理: **在庫調整ありで確定** → API 送信 → 失敗（再試行必要）。この時点で在庫調整・履歴は未送信。再試行でメタだけ更新すると、メタ上は「完了」だが在庫調整・履歴は未送信。これを避けるには「失敗時は在庫調整・履歴も送っていない」ので、再試行時に「メタ更新だけ」やると、在庫は実店舗とメタが不整合になる。なので **失敗時は「在庫調整・履歴は送っていない」** と明示し、再試行は「メタ更新のみ」＝ステータスと groupItems の反映だけにする。在庫調整・履歴は「初回確定で API が ok を返したときだけ」送る。つまり再試行必要になった場合、在庫調整はまだ行われていない。ユーザーに「在庫調整は完了していますか？」と聞くのは現実的でないので、**再試行時もサーバー側で「ペイロードに含まれる groupItems でメタを更新する」だけ**にし、在庫調整・履歴は「確定API が ok を返したときのみクライアントが送る」とする。すると、再試行必要＝初回で API が失敗した＝在庫調整・履歴は送っていない。再試行でメタだけ更新すると、メタ上は「そのグループは確定済み」になるが、在庫数は実店舗でまだ調整されていない可能性がある。  
  - 結論: 現状の仕様を維持する。「確定」押下時に、在庫調整が必要なら「先に API（メタ更新）を送り、成功したら在庫調整＋履歴を送る」。API が失敗したら再試行必要。再試行時は「メタ更新のみ」で、**在庫調整・履歴は再試行では送らない**（初回で失敗しているので、ユーザーは「在庫調整はまだ」と解釈するか、別途「在庫調整」を再度実行する必要がある）。ドキュメントに「再試行はメタ更新のみ。在庫調整・履歴が未送信の場合は、再試行後に別途在庫調整を行うか、最初から確定をやり直すこと」と書いておく。  
  - もしくは: 失敗時に「在庫調整・履歴は送っていない」ので、再試行ボタンは「メタ更新のみ」とし、**メタ更新が成功したあと、クライアントが在庫調整・履歴を送る**ようにする（再試行＝メタ更新 API を再度呼ぶ。成功したら、そのとき限り「在庫調整・履歴を送る」フラグを付けて…… いや、それだと再試行時に在庫調整が二重になる。やはり「再試行＝メタ更新のみ」で、在庫調整・履歴は初回で API が成功したときだけ、とするのがシンプル。

## 7. まとめ

| 項目 | 内容 |
|------|------|
| 待機時間短縮 | サーバー側で自動リトライ（2〜3 回）し、一時的な失敗で諦めない。案B（202 即返し）は今回は見送り。 |
| 自動リトライ | メタ破損系以外を 2〜3 回リトライ。 |
| 失敗時表示 | 対象棚卸ID・グループ、在庫調整完了・ステータス更新が必要である旨を表示。ステータスは「再試行必要」。 |
| ボタン | 確定 → 「再試行（メタ更新のみ）」に変更。 |
| API データ保持 | 受信ペイロードをメタ 1 本にバックアップ。成功時に削除。再試行は countId のみでサーバーがバックアップから復元可能。 |
| 編集不可 | 再試行必要のあいだは商品リスト編集不可。メタ更新のみ再試行可能。 |
| 管理画面 | バックアップに countId がある棚卸を「再試行必要」表示し、編集不可＋再試行ボタンのみ。 |

この設計で実装を進められる。
