# 入庫メモ（note）の形式差と在庫調整履歴の要因

管理画面の入出庫履歴で「予定外入庫」の JAN・オプションが反映されないものとされるものがあること、および「在庫調整履歴」が無いもの・同じ内容が2回出るものがあることの要因をまとめる。

---

## 1. 予定外入庫の「反映できている」と「反映できていない」の要因

### メモの2つの形式

| 形式 | 例 | 出力元 | 管理画面での表示 |
|------|-----|--------|------------------|
| **形式A** | `  - 商品名, オプション: White / iPhone16, SKU: xxx, JAN: 4589..., 予定外/数量: 2` | 入庫タイル拡張 | 商品名・オプション・SKU・JANを正しく分解して表示できる |
| **形式B（旧）** | `  - 商品名 / Silver / iPhone15Pro, SKU: xxx, 数量: 1` | 入庫拡張（旧バージョン） | 行に「オプション:」「JAN:」が無いため、オプションはタイトルに含まれたまま・JANは空になる |
| **形式B（新）** | `  - 商品名, オプション: Silver / iPhone15Pro, SKU: xxx, JAN: xxx, 数量: 1` | 入庫拡張（オプション・JAN出力対応後） | 形式Aと同様に正しく表示できる |

### なぜ「反映できていない」IDがあるか

- **反映できているID**: メモが**形式A**、または**形式B（新）**で保存されている。  
  行に「オプション: …」「JAN: …」が含まれるため、管理画面の正規表現で取得し、商品名・オプション・SKU・JANを分けて表示できる。
- **反映できていないID**: メモが**形式B（旧）**で保存されている。  
  入庫拡張が「オプション」「JAN」をメモに出力する**前**のバージョンで入庫確定したため、行が次の形になっている。
  - `  - 商品名 / オプション1 / オプション2, SKU: xxx, 数量: N`
  - オプションは**タイトル文字列に「 / 」で含まれている**が、「オプション:」というキーが無い。
  - JAN はメモに書かれていない（当時は未出力、またはバーコード未登録）。
- メモは**確定した時点で Shopify に保存される**ため、過去の確定分のメモは書き換わらない。  
  そのため、**同じ日時以降の確定でも、デプロイ前は形式B（旧）、デプロイ後は形式B（新）**となり、反映の有無が混在する。

### 対策（運用・今後のデータ）

- **今後の入庫**: 入庫拡張を「オプション・JANをメモに出力する」バージョンにデプロイ済みであれば、新規確定分は形式B（新）となり、管理画面で正しく表示される。
- **過去データ**: メモを編集しない限り形式は変わらない。管理画面側で**形式B（旧）のフォールバック**として「タイトルに『 / 』が含まれる場合は、先頭を商品名・残りをオプションとして表示する」処理を入れると、過去分もオプション列に表示できる（JANはメモに無いため復元不可）。

## 2. 在庫調整履歴が「記載されていない」／「同じ内容が2回」の要因

### メモの追記の仕組み（2026-02 以降：1回追記に変更）

入庫確定時に、メモは**1回だけ**追記される（`appendInventoryTransferNote_` を1回だけ呼ぶ）。

- **追記タイミング**: 在庫の受入・調整（予定分の入庫、予定外の入庫先プラス・出庫元マイナス、拒否の出庫元戻し）を**すべて実行したあと**、確定処理の最後で追記する。
- **1回のブロックに含める内容**  
  「[POS入庫処理] 日時」「状態: 完了」に加え、  
  メモテキスト・**予定超過**・**予定外入庫**・**在庫調整履歴**をまとめて1本で追記する。

これにより、以前あった「2回目の追記（在庫調整履歴だけ）が失敗して在庫調整履歴がメモに残らない」事象を防いでいる。  
（以前は1回目に予定外ブロック、2回目に在庫調整履歴ブロックを追記する設計で、2回目が失敗すると在庫調整履歴だけ欠けていた。）

### 在庫調整履歴が記載されていない要因

- 在庫調整ブロックは **「拒否（rejected）または予定外（extras）が1件以上あるとき」** だけ追加される（`rejectedDeltas.length > 0 || extraDeltasMerged.length > 0`）。
- 次のような場合、**2回目の追記が行われない**ため、在庫調整履歴が無いように見える。
  - 拒否も予定外も無い入庫（予定どおりのみ）→ 在庫調整ブロックはもともと書かない設計。
  - 予定外はあるが、2回目の `appendInventoryTransferNote_` の**前**でエラーが発生し、`catch (_) {}` で握りつぶされている。
  - 出庫元の locationId が取れない等で、調整用の `adjustments` が空のままの場合（条件によりブロックを出さない実装になっている可能性）。

### 同じ内容が2回記載されているように見える要因

- **2026-02 以降**: 1回の確定でメモは**1ブロックだけ**追記するため、「予定外」と「在庫調整履歴」が別ブロックで2回並ぶことはない。
- **過去データ**: 変更前は1回の確定で「予定外ブロック」と「在庫調整履歴ブロック」の2ブロックを追記する設計だったため、古いメモでは「[POS入庫処理] 日時」「状態: 完了」が2回続いて見えることがある。
- **本当に同じ文言が2回**: 確定を2回実行した場合などに、同じ内容のブロックが2つ追記されることがある。その場合は確定の二重実行などを疑う。

### 例：予定外ブロックが2回だけ並び、在庫調整履歴が1つも無い場合

メモが次のような形になっている場合（日時だけ違う「予定外入庫」ブロックが2つ、在庫調整履歴は無い）:

```
[POS入庫処理] 2026-02-20 10:36
状態: 完了
予定外入庫: 3件
  - ...

[POS入庫処理] 2026-02-20 10:37
状態: 完了
予定外入庫: 3件
  - ...（同上）
```

**想定される要因**:

1. **確定が2回実行された**  
   10:36 と 10:37 の2回、入庫確定（またはメモ追記が走る操作）が実行された。  
   いずれも「1回目の追記」（予定外ブロック）は成功しているが、「2回目の追記」（在庫調整履歴ブロック）は**どちらの確定時にも行われていない**。

2. **2回目の追記（在庫調整履歴）が失敗していた**  
   処理の流れは「1回目: 予定外ブロックを追記 → 在庫調整API実行 → 2回目: 在庫調整履歴ブロックを追記」です。  
   2回目の `appendInventoryTransferNote_` が失敗（APIエラー・ネットワーク・Transfer のステータスでメモ編集不可など）すると、`catch (_) {}` でエラーが握りつぶされるため、**在庫調整履歴だけがメモに残らない**ことがあります。  
   在庫そのもの（入庫先プラス・出庫元マイナス）は先に API で反映されているため、確定処理としては完了しており、ユーザーにはエラーが出ていません。

3. **1回目の確定でエラーが出て途中終了した可能性**  
   1回目（10:36）の確定で、予定外ブロック追記の直後、在庫調整 API やその後の処理で例外が発生した場合、2回目の追記まで到達せず終了します。  
   その場合、ユーザーには「入庫確定エラー」のトーストが出る想定です。  
   その後 10:37 にもう一度確定を実行すると、再度「予定外ブロック」だけが追記され、同じように2回目追記まで届かなければ、結果として「予定外ブロックが2つ・在庫調整履歴なし」になります。

**まとめ**: 予定外はあるのに在庫調整履歴が無く、かつ「予定外」ブロックが複数ある場合は、**確定の複数回実行**と、**在庫調整履歴の追記失敗（または追記前にエラーで終了）**が組み合わさった結果と考えられます。  
アプリ側では管理画面の問題としてトーストは出さない方針のため、2回目追記の失敗は画面上には表れません。

---

## 3. まとめ

| 事象 | 主な要因 |
|------|----------|
| 予定外の JAN・オプションが反映されない | メモが形式B（旧）で保存されている（「オプション:」「JAN:」が行に無い）。過去の確定またはデプロイ前の入庫拡張で書かれたデータ。 |
| 予定外の JAN・オプションが反映される | メモが形式Aまたは形式B（新）で保存されている（行に「オプション:」「JAN:」がある）。 |
| 在庫調整履歴が無い | 拒否・予定外が無い、または2回目のメモ追記でエラー・条件により追記されなかった。 |
| 同じ内容が2回（ブロックが2つ） | 1回の確定で「予定外ブロック」と「在庫調整履歴ブロック」を分けて追記する設計のため、日付・「状態: 完了」が2回出るのは仕様。本文が完全に同一の場合は二重送信等を疑う。 |
