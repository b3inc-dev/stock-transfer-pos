# 出庫依頼

2026-11-25。出庫依頼の管理画面・POSタイル。受領は既存の「入庫」で行い、このタイルには入庫操作を追加しない。

## 業務と画面

1. 管理画面「出庫依頼」で、出庫元・移動先・SKU／商品・数量・希望出庫日・備考を登録する。
2. 下書きは店舗に表示しない。「店舗へ依頼する」で発行する。この時点では在庫・Shopify Transferを変更しない。
3. 出庫元店舗のPOS「出庫依頼」で作業を開始し、依頼書を印刷し、スキャン・手入力で検品する。
4. 「出庫完了」で最新の設定・商品・依頼版をサーバーで確認する。差異があれば、過少・過剰・依頼外のSKU、依頼数、出庫数、符号付き差分、理由を1つのモーダルへ表示する。「確認して出庫」を押すまで在庫は動かさない。
5. 実数量でTransferを作り、Shipmentを作成・発送中にする。移動先店舗は既存の「入庫」で受領する。

通常の「出庫」は店舗が自分で内容を決める機能。「出庫依頼」は管理側の明細を店舗が実行する機能。出庫・入庫を二重実装しない。

- 管理：一覧・出庫元／状態フィルター・依頼番号／備考検索、詳細・履歴、作成／編集、差異設定、Shopifyの受領状況の参照。
- POS：出庫待ち／履歴、店舗ごとの依頼、検品、保存・端末での再開、印刷、差異確認、出庫結果の確認・再開。
- 1依頼は出庫元1つ・移動先1つ。異なる有効なLocationを選ぶ。商品はvariantId／inventoryItemIdで識別し、SKUだけを主キーにしない。
- 数量は0〜999999の整数（依頼数量は1以上）。最大3000明細。Shopifyの250明細上限ごとにTransferを分け、すべてのTransfer／Shipment IDを依頼に保存する。
- スキャンは既存明細を優先する。同一コードが明細内で複数候補の場合は自動選択しない。依頼外検索でも候補が取り切れない場合は自動確定しない。
- CSV一括登録、複数店舗への一括発行、受領操作は初版に追加しない。

## 商品追加（利用者の追加指示）

下書き・依頼中・作業中の依頼へ商品を追加できる。作業中は既存数量の追加も可能だが、既存行の削除・数量減少・出庫元／移動先の変更はできない。

作業中に追加した場合も検品実数は勝手に増やさない。依頼のversionを進め、旧版での保存／確定を拒否する。POSで「読み直す」を押すと手元の検品を保ち、新しい依頼行を検品0で追加する。再確認なしでは出庫できない。

出庫処理中・出庫完了は追加不可。結果不明・一部処理後の再開待ちも、実際には出庫済みかもしれないため内容変更をせず結果確認を優先する。取消済みを編集して再発行しない。

## 設定

管理画面「出庫依頼 → 差異の設定」で出庫依頼専用に設定する。通常の出庫・入庫の許可設定は変更しない。

| 対象 | 許可設定 | 理由 |
|---|---|---|
| 過少（0出庫の依頼行を含む） | 許可／禁止 | 不要／任意／必須 |
| 過剰 | 許可／禁止 | 不要／任意／必須 |
| 依頼にないSKUの追加 | 許可／禁止 | 不要／任意／必須 |

初期値はすべて禁止、許可時の理由は必須。理由は行単位で500文字まで。不要の場合は古い理由を出庫へ持ち越さない。依頼外SKUは過剰とは別に判定する。全行0では出庫できない。

用紙幅は58／80mm（初期80mm）。通常出庫の配送必須・配送会社の自由入力可否・配送会社マスター・表示対象店舗を読み取って踏襲する。配送会社・番号、任意の追跡URL・到着予定日を扱う。予定日は既存POS同様に端末のローカル日付からISOへ変換する。

検品途中は理由未入力でも保存できる。ただし依頼外／過剰を禁止している場合、その商品・数量は保存でも拒否する。確定直前は最新設定ですべて再検証する。

過少で確定した依頼は未出庫数と理由を残して出庫完了にする。出庫済み依頼への追加出庫は行わず、追加分は別の依頼で扱う。

## 状態・競合・復旧

```text
下書き → 依頼中 → 作業中 → 出庫処理中 → 出庫完了
              ↑      │           ├→ 再開待ち
              └─中止─┘           └→ 要確認
下書き／依頼中 → 取消済み
```

- DBのversion比較とトランザクションで同時操作を拒否する。作業権は署名済POS利用者＋端末に保存したランダムキーに紐付ける。別端末へキーを開示しない。
- 作業開始リクエストの前に端末キーを保存する。応答が失われても同じキーで作業結果を照会する。
- 作業引継ぎは管理画面で「作業を中止」して取り直す。保存済み検品は残し、古い端末キーと版を無効にする。
- 確認トークンは依頼版・設定版・サーバー検証済み実数・配送情報に対応する。変更があれば再確認する。
- 実行前にoperationIdと固定した明細・配送情報をDBへ保存する。activate、Transfer、Shipment、追跡情報、発送、履歴保存を段階ごとに記録する。
- Transfer作成・Shipment作成などの在庫系mutationは汎用503リトライラッパーで再送しない。明確なuserErrorsは再開待ち、応答なし・DB保存失敗などは要確認とする。
- Transfer noteの操作マーカー、保存済みID、Shipment明細・状態を照合して再開する。見つからない／候補が複数のときは、新規作成を許可しない。
- 処理中のまま停止した場合、2分経過後に結果照合を可能にする。期限が過ぎたことだけを理由にmutationを再送しない。
- 履歴は依頼ID＋inventoryItemIdの一意キーでupsertし、保存だけの再試行で在庫を再操作しない。未反映チャンクだけを進め、全チャンクの発送・履歴保存後に出庫完了とする。
- 在庫の正はShopify。新規テーブルは依頼・検品・実行参照であり、Shopifyの移動状態を別の在庫ジョブへ置き換えるものではない。

## 既存出庫・入庫との接続

`outboundTransferMutations.js`のTransfer READY_TO_SHIP作成・Shipment下書き・追跡更新・MarkInTransitを通常出庫と共有する。通常出庫側の引数・エラー処理・下書き／準備完了機能は変更しない。

在庫追跡／ロケーション有効化は既存サーバーヘルパーを利用する。新しいInventoryLevelを出庫数量で初期化してはならず、初期数は0にする。出庫のほかに数量adjustを送らない。

既存入庫はdestination LocationとShipmentの有無で一覧を作る。その条件に合うTransfer／Shipmentを作成するため、依頼専用の受領APIは不要。実ストアでの表示・受領の通し確認は本番配備前に行う。

## 印刷

- mainの取置印刷安全化（#142）の共通`receiptPrinting.js`を利用する。送信がタイムアウトしても、POS側の印刷処理が終了するまで同じ控えの再送を止める。
- POS API 2026-07の新拡張だけを追加し、既存拡張を一括アップグレードしない。
- POS認証済HTMLへ相対URLでアクセス。未接続なら送信せず、同じ依頼書の同時送信を防ぐ。接続確認／送信は各20秒、タイムアウト後は自動再送しない。
- 依頼番号・版・出庫元・宛先・希望日・商品・SKU・JAN文字列・数量・理由・備考を印刷する。顧客情報・金額は扱わない。自由入力をHTMLエスケープし、CSPでスクリプトを禁止する。
- 保存・出庫と印刷は独立。再印刷でTransferや在庫を増やさない。APIの解決は送信受付であり紙の排出完了ではない。実機の紙出力は別途検証する。

## データ・アクセス

新規モデル：OutboundRequest、OutboundRequestEvent、OutboundRequestSettings。マイグレーション：`20261125180000_outbound_requests`。shop/redactは既存方針に従って依頼・設定と、cascadeで対応履歴を削除する。自社用の削除方針は変更しない。

管理画面はすべてadmin認証＋プラン判定。POSは署名済セッションのshop／利用者、有効Locationと設定された表示対象店舗、依頼のoriginを照合する。POS利用者が利用可能な対象店舗の依頼を扱うモデルであり、ShopifyのPOSスタッフ権限やスタッフごとの店舗所属を独自に同期する機能は追加していない。

未契約／契約確認失敗時に新しい在庫操作を許可しない。既に開始したoperationの照合・参照と、発送済みの履歴保存は契約判定と分ける。

## 有効化・配備前の確認

1. 標準の`prisma generate`と、対象DBへの承認済みmigrationを実施する。本番DBへこの作業中に接続／migrationはしていない。
2. 開発／検証環境で`OUTBOUND_REQUESTS_ENABLED=1`を設定する。既定は無効。管理画面とPOS APIの両方に適用する。
3. 利用プランが未決のため、新featureはPro相当で閉じる。自社用は既存ルールどおり利用可能。公開版のプラン・提供開始は配備前に別途決定する。
4. 管理で依頼を発行し、対象POSへ新タイルを追加する。Shopify CLIによる新拡張登録・releaseは承認後に行う。
5. POS実機でスキャン、差異確認、58／80mm印刷、通信切断後の復旧と、移動先の既存入庫で受領まで確認する。

通常の出庫と同じ在庫・移動系スコープを利用し、顧客／注文スコープを追加しない。mainへのマージはRender本番反映につながるため、レビュー・明示承認前に行わない。

PostgreSQL統合テストは、migration済みの検証DBを`OUTBOUND_REQUEST_TEST_DATABASE_URL`に設定した場合だけ実行する。検証で作成したランダムshopのデータだけを削除し、既存データをtruncateしない。通常は標準生成済Prismaを使用する。検証用のJSエンジンを使う場合のみ、別途インストールした公式pgアダプターのモジュールを`OUTBOUND_REQUEST_TEST_ADAPTER_MODULE`で指定できる。

このクラウドでは標準Prismaエンジン配布先が403のため、公式npmパッケージのWASMでスキーマを検証し、一時的なJSエンジン／pgアダプターで実PostgreSQLのトランザクションも確認する。追跡対象のgenerator設定や本番の依存宣言は変更しない。TLS／チェックサム検証は無効化しない。

## 2026-11-26 画面・共通化の確認基準

管理画面は「依頼一覧／作成／設定」に分け、新規作成は下書き保存→詳細で確認して公開する流れに統一する。POSの固定領域・商品行・数量・ページ送りと印刷補正は実共通部品へ寄せる。通常出庫との対応、安全な再開、実機未確認の境界は [画面・出庫・印刷の共通化要件](OUTBOUND_REQUEST_UI_REQUIREMENTS.md) を参照。
