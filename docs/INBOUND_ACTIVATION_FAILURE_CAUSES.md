# 入庫時の在庫有効化が失敗する主な理由

現状の `ensureInventoryActivatedAtLocation`（`inboundApi.js`）の処理フローに基づき、在庫有効化が失敗する原因を整理したドキュメントです。

---

## 処理の流れ（概要）

1. **フェーズ1**: 入庫対象の全 `inventoryItemId` を 50 件ずつに分け、GraphQL の `nodes(ids)` で「追跡有無（tracked）」と「そのロケーションに在庫レベルがあるか」を一括確認する。
2. **フェーズ2**: 確認結果で「追跡 OFF」または「在庫レベルなし」のアイテムについて、1 件ずつ  
   `inventoryItemUpdate(tracked: true)` → （1 秒待機）→ `inventoryActivate` を実行。  
   各アイテム最大 4 回までリトライする（アイテム間は 150ms 間隔）。
3. **フェーズ3**: 失敗として記録されたアイテムについて、再度 `nodes` で在庫レベルを確認し、実際にレベルがあれば成功扱いにする。
4. 最終的に `errors` が 1 件でも残っていれば `ok: false` を返す。

---

## 失敗する主な理由

### 1. API のタイムアウト

- `adminGraphql` は 1 リクエストあたり **20 秒**でタイムアウトする（`inboundHelpers.js`）。
- フェーズ2 は**1 アイテムずつ順番に**実行するため、アイテム数が多いと「有効化の途中でどこかのリクエストが 20 秒で切れる」ことがある。
- ネットワークが遅い・Shopify 側が重い場合も、同じリクエストがタイムアウトしやすく、そのアイテムは 4 回リトライしても失敗 → `errors` に載り、結果として在庫有効化が「失敗」になる。

### 2. フェーズ1 の一括確認が失敗・不完全

- フェーズ1 の `nodes(ids: ..., locationId: ...)` が **例外**（ネットワークエラー・タイムアウト・5xx など）を投げると、`catch` でそのチャンクの **全 ID** を「要処理」としてフェーズ2 に回す。
- その結果、本来は「既に在庫レベルがある」アイテムまで `inventoryItemUpdate` / `inventoryActivate` の対象になり、  
  リトライや「既に有効」判定に依存することになる。  
  ここで API がエラーや想定外のレスポンスを返すと、そのアイテムが `errors` に入り、在庫有効化が失敗とみなされる。

### 3. 存在しない・無効な在庫アイテム ID

- フェーズ1 で **`nodes` の結果に含まれなかった ID**（削除済み商品・打ち間違い・別アプリで削除された在庫アイテムなど）は、すべて「要処理」になる。
- フェーズ2 で `inventoryItemUpdate` や `inventoryActivate` を呼ぶと、Shopify が `userErrors` を返す（例: アイテムが存在しない、そのロケーションでは有効化できない）。
- そのメッセージが「既に有効」系でない限り、リトライしても同じエラーになり、最終的に `errors` に追加され、在庫有効化が失敗する。

### 4. 追跡 ON（inventoryItemUpdate）の失敗

- 商品の「在庫追跡」が OFF のとき、先に `inventoryItemUpdate(id, { tracked: true })` を実行している。
- ここで **権限・ポリシー・商品状態**（例: ドラフト・アーカイブ・在庫管理不可）により `userErrors` が返ると、最大 4 回リトライしても失敗し、そのアイテムは `errors` に入る。
- 追跡 ON に失敗したままでは `inventoryActivate` に進めないため、在庫有効化全体が「失敗」になる。

### 5. inventoryActivate の userErrors

- `inventoryActivate` が **userErrors** を返す場合がある（例: そのロケーションでは在庫を有効化できない、在庫ポリシー制限）。
- コードでは「already / 既に / activated / 在庫レベル / already has」といったメッセージのときだけ、別クエリで在庫レベル存在を確認し、あれば成功扱いにしている。
- 上記以外のエラー（権限・ポリシー・ロケーション制限など）は、リトライしても解消されず、`errors` に追加され、在庫有効化が失敗する。

### 6. レスポンスに inventoryLevel が含まれない

- `inventoryActivate` が **userErrors なしで成功**しても、レスポンスに `inventoryLevel { id }` が含まれない場合がある（API の仕様・遅延の可能性）。
- その場合は「inventoryLevel が返されませんでした」としてリトライするが、4 回とも同じだと `errors` に載り、在庫有効化が失敗とみなされる。
- フェーズ3 の「最終確認」で実際には在庫レベルができていれば成功に繰り上げられるが、確認クエリが失敗したり、反映が遅れていると失敗のままになる。

### 7. レート制限（429）・一時的な API エラー

- 同じ画面で「事前有効化」（画面表示時の fire-and-forget）と「確定時の有効化」が同時・近いタイミングで走ると、同じ商品に対してリクエストが集中することがある。
- Shopify の **GraphQL レート制限（429 等）** や一時的な 5xx が返ると、該当リクエストが例外になり、そのアイテムはリトライ後も失敗 → `errors` に載り、在庫有効化が失敗する。

### 8. ロケーション ID のずれ・無効

- `locationId` に **入庫先ロケーションの GID** が正しく渡っていない場合（POS の「現在の店舗」と Transfer の「入庫先」が違う・型違い・ typo）、  
  `inventoryActivate(inventoryItemId, locationId)` が無効なロケーションに対して実行される。
- その場合、Shopify がエラーを返し、在庫有効化が失敗する。  
  あとから `inventoryShipmentReceive` を呼んでも「配送先に在庫がありません」になりやすい。

### 9. 反映遅延（tracked 更新後の 1 秒では足りない）

- `inventoryItemUpdate(tracked: true)` のあと、**1 秒**待ってから `inventoryActivate` を呼んでいる。
- Shopify 側の反映が 1 秒より遅い場合、`inventoryActivate` が「まだ追跡が有効になっていない」などの理由で失敗することがある。
- リトライ間隔は 800ms × 試行回数なので、運が悪いと 4 回とも「まだ反映前」のタイミングで呼ばれ、在庫有効化が失敗する。

### 10. 並行実行による競合

- 画面読み込み時に **バックグラウンド**で同じ `ensureInventoryActivatedAtLocation` が fire-and-forget で実行され、ユーザーがすぐに「確定」を押すと、**同じ商品・同じロケーション**に対してほぼ同時に `inventoryActivate` が 2 回走ることがある。
- 片方が先に成功し、もう片方が「既に在庫レベルがある」系のエラーになる場合は、コード上の「既に有効」判定で成功にできるが、  
  エラーメッセージがそのパターンに一致しない・タイミングで level 確認が失敗すると、在庫有効化が「失敗」と判定されることがある。

---

## まとめ

| 要因 | 内容 |
|------|------|
| **タイムアウト** | 20 秒で切れるため、件数多い・遅延時に一部アイテムが失敗する。 |
| **一括確認の失敗** | フェーズ1 が落ちると全 ID が「要処理」になり、不要な API 呼び出しとエラーが増える。 |
| **無効な ID** | 削除済み・存在しない在庫アイテムは必ず userErrors で失敗する。 |
| **追跡 ON の制限** | 権限・商品状態で `inventoryItemUpdate(tracked: true)` が通らないと有効化できない。 |
| **activate の制限** | ロケーション・ポリシーで `inventoryActivate` が許可されないと失敗する。 |
| **level が返らない** | API が level を返さないと「失敗」扱いになり、最終確認で救えないと errors に残る。 |
| **レート制限・一時エラー** | 429/5xx でリクエストが落ちると、そのアイテムはリトライ後も失敗することがある。 |
| **locationId の誤り** | 入庫先と異なる・無効なロケーションだと activate が失敗する。 |
| **反映遅延** | tracked 更新後の 1 秒では足りず、activate が繰り返し失敗することがある。 |
| **並行実行** | 事前有効化と確定時有効化が重なると、片方がエラーになり失敗とみなされることがある。 |

**現在の実装方針（入庫＝Shopify 在庫移管を利用）：**

- **伝票明細（移管に含まれる商品）**: 通常は入庫先で既に有効化されている想定のため、**受領 API を先に実行**する。受領が「配送先ロケーションにアイテムの在庫がありません」系で失敗したときだけ、そのタイミングで在庫有効化を実行し、受領を 1 回リトライする。有効化が失敗した場合は受領は行わずエラーで終了する。
- **予定外入荷（伝票に含まれない商品）**: 移管に含まれないため入庫先で在庫レベルが無い可能性が高い。**在庫有効化を必須**とし、有効化に 1 回リトライしてから在庫調整（adjust）を実行する。有効化が失敗した場合は在庫調整は行わずエラーで終了する。
