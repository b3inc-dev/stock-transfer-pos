# 管理画面・入出庫履歴モーダル：商品リスト（SKU）読み込み速度

## 現象

履歴一覧からモーダルを開いたとき、378 SKU 程度で約 30 秒かかることがある。

## 要因

- **1 回の GraphQL で全件取得している**  
  `inventoryTransfer(id).shipments.lineItems(first: 250)` により、全シップメントの全 lineItems を一度に取得している。
- **Shopify API 側の負荷**  
  各 lineItem で `inventoryItem → variant → product → selectedOptions` を解決するため、件数に比例してレスポンスが遅くなる。378 件程度でも 20〜30 秒になることがある。
- **ネットワーク・ペイロード**  
  レスポンスが大きいほど転送とパースに時間がかかる。

## 実施した対策（2026-02）

### サーバー側キャッシュ（同一履歴の再表示の短縮）

- **場所**: `app/routes/app.history.tsx` の action
- **内容**: 同一 `transferId` で取得した `lineItems` / `groupedLineItems` / `transferTracking` をメモリに保存（TTL 5 分）
- **効果**: 同じ履歴を閉じてから再度開いたときは、GraphQL を叩かずキャッシュを返すため、**ほぼ即時**で表示される。
- **注意**: 履歴を更新した直後にモーダルを開いても、5 分間は古い内容が返る。必要ならキャッシュキーや TTL の見直しが可能。

## さらに短くする場合の検討（未実装）

初回表示そのものを短くしたい場合は、次のような「分割取得」が考えられる。

1. **初回は先頭 N 件だけ取得**
   - 例: `lineItems(first: 100)` で先に 100 件だけ取得し、モーダルを開いたらすぐ表を表示。
   - 残りは「続きを読む」ボタンや自動で `after` カーソルを使って追加取得。
2. **シップメント単位で取得**
   - 複数シップメント時は、1 つ目のシップメントの lineItems だけ先に取得して表示し、2 つ目以降はバックグラウンドで取得。

これらは action の引数（`cursor` / `shipmentIndex` 等）の追加や、フロントの「続きを読む」UIの実装が必要。

## まとめ

- **初回 30 秒程度**: Shopify の API 仕様とデータ量に依存する部分が大きく、アプリ側だけで大幅に短縮するのは難しい。
- **同一履歴の再表示**: キャッシュにより体感はほぼ即時になる。
- **初回も短くしたい場合**: 上記の分割取得（初回 100 件＋続きを読む）の検討が有効。
