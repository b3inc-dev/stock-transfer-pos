# アプリタイルの表示件数・ロケーション・読み込みタイミング（修正と入庫・出庫との違い）

**日付**: 2026-02-25

---

## 1. 修正した不具合の要因と対応

### ① ログインしているロケーション以外のものが表示される

**要因**

- **発注・仕入・ロス・調整**: 履歴データは **メタフィールドに全ロケーション分** が保存されており、POS では「現在ロケーションでフィルタ」して表示している。フィルタ比較に **`e.locationId === sessionLocationGid`** の厳密一致を使っていた。
- 管理画面では `locationId` を **数値**（例: `"123"`）で保存している場合があり、POS の `sessionLocationGid` は **GID**（`gid://shopify/Location/123`）のため、一致せず **フィルタが効かず全件表示** したり、逆に **0件** になったりしていた。
- **棚卸**: 初回読み込み・追加読込のどちらでも、「フィルタ後に0件なら **全件をそのまま表示**」するフォールバックがあり、他ロケーションの棚卸が表示されていた。

**対応**

- **発注・ロス・調整・仕入**: ロケーションIDを **GID形式に正規化して比較** する `normalizeLocationGidForCompare` を導入。`"123"` と `gid://shopify/Location/123` を同一とみなしてフィルタするようにした。
- **棚卸**: 「フィルタ後0件なら全件表示」のフォールバックを削除。ログイン中ロケーション以外は表示しない。

**変更ファイル**

- `extensions/stock-transfer-order/src/screens/order/OrderHistoryList.jsx`
- `extensions/stock-transfer-loss/src/screens/loss/LossHistoryList.jsx`
- `extensions/stock-transfer-adjustment/src/screens/loss/AdjustmentHistoryList.jsx`
- `extensions/stock-transfer-purchase/src/screens/purchase/PurchaseHistoryList.jsx`
- `extensions/stock-transfer-stocktake/src/screens/stocktake/InventoryCountConditions.jsx`

---

### ② 読み込み数が設定に反映されていない・表示順が古い順

**要因**

- **表示件数**: 発注・仕入・ロス・調整は **メタフィールドのチャンク** で保存・読込している。チャンクサイズ（1チャンクあたりの件数）は **管理画面で保存するとき** の設定（`historyInitialLimit`）で決まる。POS は「チャンク0」を読むだけなので、「設定の件数」は **最後に管理画面で保存したときの値** が反映される。
- **表示順**: メタフィールドのチャンク並びが **古い順** のまま表示していた。

**対応**

- 履歴一覧の **表示順を日付降順（新しい順）** に統一。`listToShow` を `date` / `createdAt` でソートしてから表示するようにした。
- 表示件数は「チャンク保存時に設定を反映」する現状の仕組みはそのまま。管理画面で履歴を保存するタイミングで、その時点の「履歴一覧リストの初回表示件数」がチャンクサイズとして使われる。

---

### ③ 一覧リストから「次の一覧・商品リスト」を読み込むタイミング（入庫・出庫と同様に統一）

**結論: 全タイルで「一覧は軽く・タップ後に詳細を扱う」形に統一済み（一覧画面でのフリーズが短い）**

| タイル | 一覧の読み込み | 詳細・商品リストの読み込み |
|--------|----------------|----------------------------|
| 出庫   | タイルを開いたとき。API でロケーション指定して取得。 | **タップ後**：詳細画面へ遷移し、シップメント情報を表示（必要なら追加API）。 |
| 入庫   | タイルを開いたとき。API でロケーション指定して取得。 | **タップ後**：`loadShipment(id)` でシップメント・明細を取得。 |
| 発注・ロス・調整・仕入 | タイルを開いたとき。**一覧用は `items` を落とした軽いデータのみ state に保持**（`stripEntryForList`）。フルデータは ref に保持。 | **タップ後**：ref からフルエントリ（`items` 含む）を取得して詳細表示。追加APIは呼ばず、既読込分から即表示。 |
| 棚卸   | コンディション画面で `refresh`（初回＋読込ボタン）。ロケーションでフィルタ。 | **タップ後**：棚卸IDをタップ → グループ選択 → `onNext` で商品リストへ遷移し、その後に商品取得（STOCKTAKE_UX_TAP_AND_LOAD_BUTTONS.md のとおり「先に遷移、後で更新」）。 |

発注・仕入・ロス・調整は、一覧用に **`items` を持たないエントリだけを state に置き**、フルエントリは **ref（fullEntriesByIdRef）** に保持するように変更済み。タップ時に ref から詳細を出すため、**一覧の初回描画が軽く**なり、入庫・出庫に近い操作感になっている。

## 2. 入庫・出庫と発注・仕入・ロス・調整の違い（要因の整理）

| 項目 | 入庫・出庫 | 発注・仕入・ロス・調整 |
|------|------------|------------------------|
| **データの持ち方** | 管理画面 API（GraphQL）で **ロケーション指定** して取得。`fetchTransfersForOriginAll(originLocationGid, { first })` / `fetchTransfersForDestinationAll(locationGid, { first })` など | **メタフィールド** に全ロケーション分を保存。POS は「チャンク0」等を読んで **クライアントで現在ロケーションのみフィルタ** |
| **ロケーション絞り** | **API 側でロケーション指定** しているため、最初から「そのロケーションのデータ」だけ返る | **API は全ロケーション**。表示は **POS 側で `sessionLocationGid` と正規化した `e.locationId` の一致** で絞る |
| **表示件数の反映** | API の `first` に **設定の履歴一覧リスト件数** を渡しているので、取得件数＝表示件数で一致 | チャンクサイズが **管理画面で保存したときの設定** で決まる。POS はそのチャンクを読むだけ。今回 **日付降順ソート** で表示順を統一 |
| **タップ後の読み込み** | **入庫**: `loadShipment(id)` でシップメント・明細を取得。<br>**出庫**: 選択した transfer の情報は状態で保持し、詳細画面で必要に応じて取得 | **タップ後**に ref からフルエントリ（`items` 含む）を取得して表示。一覧 state は軽いので **追加APIは不要**。画像は必要なら別取得。 |

この違いのため、

- **入庫・出庫** は「ロケーション指定の API」なので他ロケーションは元々返ってこず、表示件数も API の `first` で制御されている。
- **発注・仕入・ロス・調整** は「全ロケーション入りメタフィールド」なので、**クライアント側のロケーション正規化とフィルタ** が必須で、あわせて **日付降順** で表示順を揃えた。

## 3. 表示件数・並び順・ロケーションの5タイル統一（棚卸・仕入・発注・ロス・調整）

| 項目 | 棚卸 | 仕入 | 発注 | ロス | 調整 |
|------|------|------|------|------|------|
| **表示件数** | 設定の履歴一覧リスト（初回読込件数）をチャンク／first に反映 | 同上（チャンク保存時に反映） | 同上 | 同上 | 同上 |
| **並び順** | 日付降順（新しい順） | 日付降順 | 日付降順 | 日付降順 | 日付降順 |
| **ロケーション表示** | ログイン中ロケーションでフィルタ（`filterByLocation`）。0件でも他ロケーションは表示しない。 | ログイン中のみ表示（`normalizeLocationGidForCompare` で GID/数値両対応） | 同上 | 同上 | 同上 |

5タイルとも「表示件数は設定の履歴一覧リスト」「並びは新しい順」「表示は現在ロケーションのみ」で揃えている。
