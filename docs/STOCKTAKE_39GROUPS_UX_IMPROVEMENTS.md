# 棚卸 39 グループ・約 5600 SKU 時の遅延解消と UX 改修方針

**日付**: 2026-02

## 目的

39 グループ・合計約 5600 SKU の棚卸IDでも遅延を感じず、かつ「まとめて表示で未保存グループが商品がありませんのまま」にならないようにする。

---

## 1. 改修の最適解（画面別）

### 1.1 まとめて表示（ID を開いたときの商品リスト）

**現状**: 全グループを for で直列に fetch するため重い。未完了で自動保存されていないグループは商品リストを読まず「商品がありません」になる。

**最適解**: **入庫・出庫の「要読込＋読込ボタン」と同様に、グループごとに「読込」で読み込む**

- **初期表示**
  - 全 39 グループ分の**見出し（グループ名）だけ**を並べて表示する。各グループの商品リストは**読まない**。
  - 各グループのブロックに「未読込」または「要読込」と「読込」ボタンを表示する。
- **読込ボタン**
  - ユーザーがそのグループの「読込」を押したときだけ、**その 1 グループ分**だけ `fetchProductsByGroups([そのgroupId], ...)` を実行する。
  - 読み込んだ結果をそのグループの lines として表示し、必要なら下書き保存対象にする。
- **効果**
  - 開いた瞬間の API 呼び出しをほぼゼロにでき、体感が軽い。
  - 必要なグループだけ読むので、39 グループ全部を読まなくてよい。
  - 自動保存されていないグループも「読込」で読めるので、「商品がありません」のままにならない。

**実装のポイント**

- まとめて表示時は `loadProducts` で**全グループを一括で読まない**。代わりに「グループ一覧（名前のみ）」と「未読込」状態を表示。
- グループごとに「読込」が押されたら、その `groupId` だけ `fetchProductsByGroups([groupId], ...)` を呼び、得た商品を `lines` のうちそのグループのセクションに反映（例: `linesByGroup` 的な状態を 1 グループ分だけ更新）。
- 既に読み込み済みのグループは「読込」を非表示または「再読込」に変更。

---

### 1.2 商品グループ一覧画面（グループを選ぶ画面）

**現状**: フッターに「再読込」があり、押すと全グループの在庫数取得（`fetchProductsByGroups` ＋ `getCurrentQuantity` 多数）が走る。初回から自動で在庫を読んでいる場合は 39 グループ分で重い。

**最適解**: **ヘッダーに「在庫数読込」ボタンを置き、押したときだけ在庫を取得する**

- **初期表示**
  - グループ名と「未読込」または「−/−」「0件」のみ表示。**在庫数は自動では取得しない**。
- **ヘッダーに「在庫数読込」ボタン**
  - 押したときだけ `loadProductGroupQuantities()` を実行し、各グループの在庫数・件数を取得して表示を更新する。
- **効果**
  - 画面を開いた直後の遅延をなくせる。
  - 在庫数が必要な人だけボタンで取得すればよい。

**実装のポイント**

- 商品グループ一覧のマウント時には `loadProductGroupQuantities` を**呼ばない**（既に呼んでいれば削除）。
- ヘッダー（またはフッターの「再読込」の横）に「在庫数読込」を明示し、「初回は押すまで在庫を表示しない」挙動にする。

---

### 1.3 商品リスト画面（単一グループ選択時）

**現状**: 単一グループ時は 1 回の `fetchProductsByGroups` と「さらに読み込む」で済んでいる。5600 SKU が 1 グループに集中している場合は、初期の offset/limit（例: 600 件）＋「さらに読み込む」で対応済み。

**最適解**: **現状の「先頭 N 件＋さらに読み込む」を維持し、必要なら初期件数のみ微調整**

- 単一グループ時は、入庫・出庫と同様「要読込」＋「読込」で追加読み込みする現状でよい。
- まとめて表示は上記 1.1 の「グループごと読込」に任せ、商品リスト画面単体では大きな変更は不要。

## 2. その他の案

| 案 | 内容 | 効果 |
|----|------|------|
| **段階表示** | まとめて表示で全グループを読む場合、1 グループ読むごとにそのグループ分だけ `setState` して表示を追加する。 | 全グループ読む場合の体感が良くなる。ただし 39 グループ全部読むと依然として時間はかかる。 |
| **並列化（上限付き）** | `fetchProductsByGroups` の 1 グループ内バッチや、複数グループを 2〜3 グループずつ並列で読む。 | 読む量が同じなら時間短縮。レート制限に注意。 |
| **在庫数の一括取得** | 1 バリアント 1 回の `getCurrentQuantity` ではなく、inventoryItemIds をまとめて在庫レベル取得する API を利用する。 | 在庫取得のラウンド数が減り、全体が軽くなる。 |

まとめて表示は「グループごと読込」にすると、上記を組み合わせる必要は最小限で済む。

## 3. 商品リストのヘッダーで「商品グループ名が違うグループ名になる」要因と修正

### 3.1 要因

商品グループ名は **`productGroupNames`（Map）** で `groupId` → 表示名 を保持し、表示時に `productGroupNames.get(groupId)` で名前を取っている。

**不整合が起きる理由**:

1. **ID の形式が揃っていない**
   - `count.productGroupIds` やメタフィールドには **GID**（`gid://shopify/.../123`）で入ることがある。
   - 一方、`readProductGroups()` の `group.id` や、別経路で渡る `groupId` が **数値や文字列の "123"** になっていることがある。
   - Map のキーに **GID で set** しているのに、表示時は **"123" で get** している（またはその逆）と、`get` が `undefined` になり、フォールバックで **raw の groupId**（長い GID や "123"）がそのまま表示される。

2. **indexOf による配列インデックスのずれ**
   - 名前の初期値は `count.productGroupNames[count.productGroupIds.indexOf(id)]` で取っている。
   - `id` が GID で `productGroupIds` が数値だけ（または逆）だと `indexOf(id)` が **-1** になり、`productGroupNames[-1]` は `undefined`。その結果、`getProductGroupName(id)` で取得した名前で Map に **別形式のキー**（例: "123"）で set される。
   - 表示側では別形式（例: GID）の `groupId` で get するため、やはり undefined → 間違った表示になる。

3. **39 グループ・5600 SKU で顕在化する理由**
   - データ量が増えると、メタフィールドや props の経路で ID が正規化されずに渡りやすい。
   - 管理画面と POS、または POS 内の「count 由来」と「readProductGroups 由来」で ID 形式が混在すると、上記のずれが起きる。

### 3.2 修正方針

**Map のキーを「正規化した ID」に統一する。**

- **設定時（set）**: `count.productGroupIds` / `targetProductGroupIds` / `getProductGroupName(id)` で名前を入れるとき、キーに **正規化 ID** を使う。  
  - 例: `normalizeIdForMatch(id)`（`stocktakeApi.js` にある、GID の最後のセグメントを取る関数）の結果をキーにする。
- **参照時（get）**: 一覧や商品リストで `productGroupNames.get(groupId)` するときも、**同じ正規化**をかけたキーで get する。  
  - 例: `productGroupNames.get(normalizeIdForMatch(groupId))` または、正規化キーで Map を構築しておき、表示は常に正規化キーで参照する。

これで、GID と数値 ID が混在していても、同じグループは同じ名前になる。

### 3.3 修正箇所（コード）※実装済み

- **stocktakeApi.js**
  - `normalizeIdForMatch` を export した。
- **InventoryCountList.jsx**
  - 商品グループ名を set する useEffect 内で、Map のキーを `normalizeIdForMatch(id)` に統一（initialMap と loadNames の groupMap）。
  - 名前の取得は `count.productGroupIds.indexOf(id)` を `findIndex((pid) => normalizeIdForMatch(pid) === normalizedId)` に変更し、ID 形式が混在しても正しいインデックスで名前を取得。
  - ヘッダーの `groupNameText`：まとめて表示で `count.productGroupNames` が無い場合は `targetProductGroupIds.map((id) => productGroupNames.get(normalizeIdForMatch(id)) || id).join(", ")` で表示。
  - まとめて表示の各セクションの `groupName`：`productGroupNames.get(normalizeIdForMatch(groupId)) || groupId` で取得するように変更。

---

## 4. 実装の優先順位

1. **商品グループ名の不整合修正**（正規化キーで Map を統一）  
   → すぐに効果があり、他の改修と独立して実施可能。

2. **まとめて表示の「グループごと読込」**  
   → 遅延解消と「商品がありません」解消の両方に効く。

3. **商品グループ一覧の「在庫数読込」ボタン**  
   → 一覧画面の初回表示を軽くする。

4. （任意）単一グループ時の初期件数や、在庫一括取得などの追加最適化。

この順で進めると、39 グループ・5600 SKU でも遅延を抑えつつ、表示の不整合も解消しやすい。

---

## 5. POS の表示遅延ストレスがない目安の上限と現状・最適解

### 5.1 前提（POS の制約）

- **GraphQL タイムアウト**: 1 リクエスト 20 秒（`stocktakeApi.js`）。
- **商品取得**: `nodes(ids)` は 50 件ずつバッチ。在庫数は `getCurrentQuantity` を 15 件ずつ実行。
- **単一グループの初回**: offset 0・limit 600 で最大 600 件まで。それ以上は「さらに読み込む」で 600 件ずつ追加。
- **まとめて表示**: グループごとに `fetchProductsByGroups` を **直列** で呼ぶため、グループ数 ×（1 グループあたりの処理時間）だけかかる。

### 5.2 ストレスなく表示される目安の上限

| 対象 | 目安の上限（目安） | 理由 |
|------|-------------------|------|
| **1 棚卸IDあたりのグループ数** | **5〜10 グループ**（まとめて表示で一括読む現状の場合） | 1 グループあたり 数秒かかると、直列で 10 グループで 20 秒前後。それ以上は開いた瞬間の待ちが長くなり遅延ストレスが出やすい。 |
| **1 商品グループあたりの SKU 数** | **300〜600 SKU** | 初回 1 回の fetch で 600 件まで取得。在庫取得が 600÷15＝40 バッチ程度で 20 秒内に収まりやすい。1000 超えると「さらに読み込む」前提になり、初回表示後も読込が増えて体感が重くなりやすい。 |

- **まとめて表示を「グループごと読込」にした場合**: 開いた瞬間に読むのは「見出しだけ」なので、**棚卸IDのグループ数は 20〜30 でもストレスなし**。各グループの商品は「読込」を押したときだけ取得するため、**1 グループあたりの SKU 数**は上記の 300〜600 を目安にすればよい。
- **単一グループ表示**: 1 グループだけなので、そのグループの SKU が 600 以内なら初回が軽い。600 超は「さらに読み込む」で補う現状の組み方でよい。

### 5.3 現在の組み方が最適か

| 項目 | 現状 | 最適解の方向性 |
|------|------|----------------|
| **単一グループの商品リスト** | 初回 600 件＋「さらに読み込む」で 600 件ずつ。limit 最大 2000。 | **現状のままでよい**。初回 600 は体感と API 負荷のバランスが取れている。 |
| **まとめて表示** | 全グループを for で直列に fetch。グループ数が多いと開いた瞬間に重い。 | **グループごと「読込」**にすると、開いた瞬間は見出しのみで軽く、必要なグループだけ読める。グループ数上限を気にしにくくなる。 |
| **商品グループ一覧（グループ選択画面）** | 再読込で全グループの在庫数取得。グループ数が多いと重い。 | **在庫数は「在庫数読込」ボタンで取得**にすると、初回表示は軽く、必要なときだけ在庫を読める。 |
| **1 グループあたり SKU 数** | コード上は 1 回あたり最大 2000（limit）まで。初回は 600。 | **運用目安として 300〜600** にしておくと、初回表示が 1 回で収まりストレスが少ない。それ以上は「さらに読み込む」前提。 |

結論として、**単一グループ・初回件数（600）は現状の組み方でよい**。遅延ストレスを減らすなら、**まとめて表示を「グループごと読込」**にし、**商品グループ一覧で在庫数をボタン読込**にすることが最適解に近い。それにより「棚卸IDのグループ数」「1 グループの SKU 数」の上限を、体感しやすい目安（上表）に収めやすくなる。
