# 棚卸「まとめて表示」で2つ目以降の商品リストが読み込まれない要因

**日付**: 2026-02-16

## 事象

- 本番で棚卸の「まとめて表示」を使うと、1つ目の商品グループのみ商品リストが表示され、2つ目以降は「商品がありません」のままになる。
- 「商品グループごとに選択」で該当グループを開くと、そのグループの商品リストは表示される。

## 要因

### 1. 棚卸作成時に `inventoryItemIdsByGroup` が全グループ分入っていない

**流れ:**

- POS の「まとめて表示」では、`count.inventoryItemIdsByGroup` を参照して、**グループごとの inventoryItemId 一覧**で商品を取得している（`fetchProductsByGroups` → `savedInventoryItemIds`）。
- `inventoryItemIdsByGroup` は**管理画面で棚卸IDを発行したとき**に、その時点の「商品グループ」の `inventoryItemIds` をコピーして保存している。
- 管理画面のロジックでは、**「グループに既に `inventoryItemIds` が入っているときだけ」** そのグループを `inventoryItemIdsByGroup` に載せていた。

```ts
// 旧ロジック（要因）
if (group.inventoryItemIds && group.inventoryItemIds.length > 0) {
  inventoryItemIdsByGroup[groupId] = [...group.inventoryItemIds];
}
```

- 商品グループの `inventoryItemIds` は、
  - そのグループを**編集して保存**したとき（コレクションやSKUから商品を取得したとき）、または
  - CSVでSKUを登録したとき  
  にだけセットされる。
- そのため、
  - 1つ目のグループは過去に編集保存されていて `inventoryItemIds` がある → 棚卸作成時に `inventoryItemIdsByGroup` に含まれる → POS で商品リストが読める。
  - 2つ目以降のグループは「名前＋コレクション選択だけ」で、一度も「保存」で商品取得していない → `inventoryItemIds` が空 → 棚卸作成時に `inventoryItemIdsByGroup` に**含まれない** → POS では `inventoryItemIdsByGroup` にキーが無いため、コレクション取得にフォールバックするが、POS 側の `readProductGroups()` のグループに `collectionIds` が無い／別要因で 0 件になる → 「商品がありません」になる。

まとめると、

- **「棚卸作成時点で、そのグループに `inventoryItemIds` が入っていないと、`inventoryItemIdsByGroup` にそのグループが載らない」**
- その結果、POS のまとめて表示では 2つ目以降のグループ用の商品リストが取得できず、商品が表示されない。

### 2. 既存の棚卸IDについて

- すでに発行済みの棚卸IDは、**発行時に上記の旧ロジックで保存されている**ため、`inventoryItemIdsByGroup` に 2つ目以降が入っていない可能性が高い。
- そのため、
  - **新規に発行する棚卸ID**は、今回の管理画面側の修正により、全グループ分の商品IDが入るようになる。
  - **既存の棚卸ID**は、現状のままだと 2つ目以降が空のままなので、「まとめて表示」では 2つ目以降が「商品がありません」のままになる。

## 対応内容（コード側）

1. **管理画面（棚卸ID発行時）**
   - 発行時に「選択した全商品グループ」について、その時点で `inventoryItemIds` が空でも、
     - コレクションがあればコレクションから、
     - なければ SKU から  
     商品を取得して `inventoryItemIds` を組み立て、**全グループ分**を `inventoryItemIdsByGroup` に保存するように変更した（`getInventoryItemIdsForGroup` を追加し、発行処理で利用）。
   - これにより、**新規発行する棚卸ID**では、まとめて表示で全グループの商品リストが読まれるようになる。

2. **既存の棚卸ID**
   - コードでは「既存の count を書き換える」処理は入れていない。
   - 既存の棚卸で 2つ目以降も表示したい場合は、
     - その棚卸を**使わず、あらためて棚卸IDを発行し直す**か、
     - 必要であれば「既存棚卸の `inventoryItemIdsByGroup` を補完する」機能を別途検討する必要がある。

## 確認方法

- 管理画面で**新しく棚卸IDを発行**し、複数商品グループを選択して発行する。
- POS でその棚卸IDを開き、「まとめて表示」を選ぶ。
- 全グループで商品リストが表示されることを確認する。

## 管理画面が 502 になる要因（発行直後に発生した場合）

棚卸ID発行後、管理画面が 502 Bad Gateway になることがある。

**想定要因**

- 発行時に「全グループ分の inventoryItemIds」を取得するため、グループ数 × コレクション数ぶんの GraphQL が**直列**で実行される。
- グループが多く、かつ各グループに `inventoryItemIds` が未保存（コレクション/SKU からその場で取得）だと、処理時間が長くなり、**ホスティングのリクエストタイムアウト（例: Render 30 秒）を超える**と 502 になる。
- その間ブラウザは待ち続けるため、発行ボタン押下〜しばらくしてから 502 になる、という動きになる。

**対応（コード側）**

- 取得処理に**時間予算**（例: 22 秒）を設け、超えたら残りのグループはスキップし、取得できた分だけ `inventoryItemIdsByGroup` に載せて棚卸を保存する。
- グループごとに **try/catch** し、1 グループで失敗しても他は続行し、取得できたグループだけ保存する。

これにより、タイムアウトによる 502 を避けつつ、可能な範囲で全グループ分を保存する。  
グループ数が多くて時間内に終わらない場合は、「商品グループ設定」で各グループを一度編集保存（コレクションから商品取得）してから棚卸IDを発行すると、既存の `inventoryItemIds` が使われて発行が軽くなる。

### 39 グループ・約 5800 商品で「Application Error」になる要因と対策（2026-02）

- **要因**: ①発行処理のどこかで未捕捉の例外（GraphQL エラー・メタフィールド保存失敗・ネットワーク等）が発生すると Remix の ErrorBoundary が表示され「Application Error」になる。②メタフィールド値の合計が大きすぎる（39 グループ×約 5800 の inventoryItemId を保存すると JSON が 500KB 超になりうる）と、保存失敗やリクエストタイムアウトで例外になる。
- **対策（実装済み）**: ①`create_inventory_count` 全体を try/catch で囲み、例外時は「棚卸IDの発行中にエラーが発生しました。時間をおいて再度お試しください。」を返して Application Error を出さない。②保存前の JSON サイズが 500KB を超える場合は、その棚卸だけ `inventoryItemIdsByGroup` を保存せず（`inventoryItemIdsOmittedDueToSize` を付与）、棚卸は発行成功とする。POS ではコレクションから商品を読み込む。③時間予算を 22 秒→25 秒に延長してタイムアウトを少し緩和。

### 500 エラーを「そもそも起こさない」ための予防策（2026-02）

- **なぜ 500 が出るか**: Shopify の GraphQL は、レート制限（スロットル）やクエリエラー時に **HTTP 200 のまま** レスポンス本文に `errors` を返す。アプリで使っている Shopify クライアントは、この `errors` を見つけると例外を投げる。Remix では未捕捉の例外が 500 になる。
- **大量処理だと防げないか**: 完全には防げない（ネットワーク障害・Shopify 側の一時エラーはこちらでは防げない）。ただし **発生しやすさは減らせる**。
- **予防策（実装済み）**  
  1. **1回あたりのグループ数上限（30 グループ）**  
     一度に発行できる商品グループを 30 までに制限。それ以上は「複数回に分けて発行してください」と案内。リクエスト数・処理時間・メタフィールドサイズを抑え、タイムアウトやスロットルを起こしにくくする。  
  2. **グループ間の待機（120ms）**  
     各グループの `getInventoryItemIdsForGroup` のあとに 120ms 待ってから次を実行。GraphQL を連続で打たずに間を空け、Shopify のレート制限（ポイント/秒）に当たりにくくする。  
  3. **action 全体の try/catch**  
     上記でもなお例外（スロットル・その他 API エラー）が起きた場合は、500 ではなく「処理中にエラーが発生しました。しばらくしてからお試しください。」を 200 で返す。
- **さらに大量のとき**: 30 グループを超える場合は 2 回以上に分けて発行する運用で対応。将来的にバックグラウンドジョブで非同期発行にすれば、1 リクエストの負荷をさらに減らせるが、実装コストは大きい。

### 棚卸IDを「開いた」ときに 500 になる対策（39 グループ・約 5700 SKU 等）（2026-02）

- **事象**: 39 グループ・約 5700 SKU の棚卸IDを開いた（一覧でクリックしてモーダルを開く、または棚卸ページを開く）ときに 500 が発生する。
- **要因**: ①**loader**でメタフィールド（棚卸一覧・商品グループ）を取得する際、データが非常に大きいと GraphQL レスポンスのパースやクライアントの例外で 500 になる。②**モーダル表示時**に未完了グループの商品リストを `get_incomplete_group_products` で取得するが、グループあたりの SKU 数が多く、バッチで多数の GraphQL を連続実行するとレート制限やタイムアウトで 500 になる。
- **対策（実装済み）**  
  1. **loader の try/catch**  
     loader 全体を try/catch で囲み、例外時は 500 にせず空のデータと `loadError: true` を返す。画面では「データの読み込みに失敗しました。ページを再読み込みしてください。」を表示。  
  2. **get_incomplete_group_products の負荷軽減**  
     - **バッチ間待機（80ms）**: 商品バッチ・コレクションループの各ステップの間に 80ms 待機し、GraphQL の連続呼び出しを抑えてスロットルを防ぐ。  
     - **1グループあたり 600 件上限**: 1 リクエストで返す商品数を最大 600 件に制限。超過分は切り捨て、`truncated: true` を返す（表示は「一部のみ」となるが 500 を防ぐ）。  
  3. **action 全体の try/catch**  
     上記でも例外が起きた場合は、500 ではなく「処理中にエラーが発生しました。しばらくしてからお試しください。」を 200 で返す。

## 「まとめて表示」で読めないグループが、グループごと表示のあとだと表示される理由

**事象**: まとめて表示では一部の商品グループだけ読み込みできていない。いったん「商品グループごとに表示」でそのグループを開いてから、再度「まとめて表示」にすると、そのグループが表示される。

### 想定される要因

1. **初回まとめて表示での直列処理とタイムアウト・エラー**
   - 「まとめて表示」では、グループごとに **for ループで直列に** `fetchProductsByGroups` を呼んでいる（`InventoryCountList.jsx`）。
   - 1つ目のグループの取得に時間がかかると、2つ目以降の処理開始が遅れる。その時点で **GraphQL の 20 秒タイムアウト**（`stocktakeApi.js` の `graphql()`）やネットワークの一時的な失敗が起きると、そのグループだけ `products.length === 0` となり、`continue` でスキップされ表示されない。
   - 「商品グループごとに表示」では **1グループだけ** `fetchProductsByGroups` が呼ばれるため、1回の取得で済み、タイムアウトやエラーが起きにくい。
   - 再度「まとめて表示」にしたときは、端末やネットワークが落ち着いている、または前回の処理でメタフィールド取得などが済んでいるため、同じグループも含めて読めるようになることがある。

2. **`inventoryItemIdsByGroup` にキーが無い場合のフォールバックの不安定さ**
   - 当該グループが `inventoryItemIdsByGroup` に含まれていない（既存棚卸 or 発行時の 502 でスキップされた）場合、POS は `readProductGroups()` のメタフィールドから `group.collectionIds` で商品を取得する。
   - 初回の「まとめて表示」で、`readProductGroups()` の GraphQL が一時的に失敗したり、メタフィールドの取得が遅れて空や不完全な結果になると、そのグループは `targetGroups.length === 0` となり 0 件になる。
   - グループごとでそのグループを開くと、**その 1 回だけ** `readProductGroups()` が呼ばれ、そのタイミングでは成功して商品が取れる。再度まとめて表示にすると、同じ `readProductGroups()` が安定して成功し、全グループが表示される。

3. **ID 形式の照合**
   - `count.productGroupIds` と `readProductGroups()` が返す `group.id` の形式（GID と数値など）が一部で一致しないと、`findInventoryItemIdsByGroupKey` / `targetGroups` の filter でそのグループが含まれず 0 件になる。正規化（`normalizeIdForMatch`）で吸収しているが、エッジケースで初回だけ不一致になる可能性がある。

### 運用上の対処

- **新規発行**では、発行時に全グループ分の `inventoryItemIdsByGroup` が入るため、まとめて表示で安定して読める。
- 既存の棚卸で「まとめて表示」の初回だけ一部読めない場合は、**一度「商品グループごとに表示」で該当グループを開いてから「まとめて表示」に戻す**と、多くの場合で表示される。
- 恒常的に読めないグループがある場合は、当該棚卸を発行し直すか、管理画面の「商品グループ設定」でそのグループを編集保存してから、棚卸IDを再発行することを検討する。

## まとめて表示で不備なく表示するためのコード改善（実装済み）

**目的**: 初回の「まとめて表示」でも全商品グループが読み込まれるようにする。

### 1. 商品グループ一覧の事前取得（1回だけ）

- **変更箇所**: `InventoryCountList.jsx`（まとめて表示モード）、`stocktakeApi.js`（`fetchProductsByGroups`）。
- **内容**: まとめて表示のループの**前**に `readProductGroups()` を **1回だけ** 呼び、取得した配列を `cachedProductGroups` として保持。各グループの `fetchProductsByGroups` 呼び出し時に `opts.cachedProductGroups` として渡す。
- **効果**: 全グループが**同じスナップショット**を参照するため、「2つ目以降のグループでだけ `readProductGroups()` が失敗する／遅れる」といったばらつきを防ぎ、初回から安定して表示しやすくする。

### 2. fetchProductsByGroups の cachedProductGroups オプション

- **変更箇所**: `stocktakeApi.js` の `fetchProductsByGroups`。
- **内容**: オプションに `cachedProductGroups`（商品グループ配列）を追加。渡された場合は `readProductGroups()` を呼ばず、この配列を使って `targetGroups` を組み立てる。
- **効果**: まとめて表示時に N 回呼ばれても、商品グループ取得の GraphQL は**事前の1回のみ**で済み、負荷と失敗ポイントを減らす。

### 3. 未完了グループの 0 件リトライ

- **変更箇所**: `InventoryCountList.jsx`（まとめて表示モード・未完了グループの商品取得）。
- **内容**: 未完了グループで `fetchProductsByGroups` の結果が 0 件の場合、**約1秒待機**してからもう1回だけ同じ条件で `fetchProductsByGroups` を実行。2回目も 0 件ならそのグループはスキップする。
- **効果**: 一時的なメタフィールド取得の遅れやネットワーク揺れで 0 件になった場合に、リトライで表示される可能性を高める。

### 確認方法

- 複数商品グループを持つ棚卸IDで、**いきなり「まとめて表示」**を選択する。
- 全グループで商品リストが表示されること、および「商品グループごとに表示」を経由しなくても初回で表示されることを確認する。

## 管理画面とアプリタイルで明細数・在庫数が一致しない事象（要因調査用・2026-02）

### 事象

- 管理画面（CSV）：明細 464、在庫数 560
- アプリタイル：明細 106、在庫数 171
- タイル側の読み込みが少なく、管理画面と数が合わない。

### 同じメタフィールドを読んでいるか

- **管理画面**も**アプリタイル（POS）**も、棚卸一覧は同じ **Shopify のメタフィールド**（`currentAppInstallation` の `inventory_counts_v1`）を読んでいる。
- ただし参照している**フィールド**が違う：
  - **管理画面の CSV**：各棚卸の **`groupItems`**（確定時に POS から保存した明細）を使って 464 件を出力している。
  - **POS の商品リスト**：  
    - そのグループが**完了**と判定されていれば **`groupItems`** を表示に使う（ここで 464 が取れていれば一致する）。  
    - **未完了**と判定されていれば、**`inventoryItemIdsByGroup`**（発行時に保存した ID リスト）で `fetchProductsByGroups` を呼び、その結果（106 件）だけ表示する。
- したがって「管理画面で 464 が出ている ＝ メタフィールドの **groupItems には 464 件入っている**」と考えてよい。問題は **POS 側でその groupItems を正しく参照できていない**可能性（＝未完了扱いになり、fetch の 106 件だけ表示している）がある。

### 棚卸IDのメタフィールドをどこで確認できるか

- Shopify 管理画面の「設定 > アプリ」から、アプリが保存したメタフィールドの**中身を直接見る**機能はない。
- 確認するには次のいずれかが必要：
  1. **管理画面アプリ側に一時的なデバッグ表示を入れる**  
     - 選択中の棚卸について、`groupItems` のキー一覧と各キーの配列長（件数）、`inventoryItemIdsByGroup` の有無・キーごとの件数、`inventoryItemIdsOmittedDueToSize` の有無を表示する。
  2. **Shopify の GraphQL**（Admin API）で `currentAppInstallation { metafield(namespace: "stock_transfer_pos", key: "inventory_counts_v1") { value } }` を実行し、返ってきた JSON を確認する。
- いずれにしても「同じメタフィールド」なので、**管理画面で 464 が取れているなら、メタフィールドには 464 のデータがある**。ずれの原因は **POS が groupItems を参照するときのキー照合**（GID と数値 ID の不一致で取れていない）の可能性が高い。

### 仮説の整理（在庫数も合わない理由）

- **在庫レベルで除外しているだけ**なら、明細数だけ少なくなり在庫数合計は一致するはず。在庫数も 171 と少ないため、**在庫を持っているはずの商品も読み込めていない**。
- 上記を踏まえると、**POS で「完了」の groupItems（464 件）をキー不一致で取れず、未完了扱いになって fetchProductsByGroups の 106 件だけ表示している**、という流れが最も説明しやすい。  
  → 対策案：POS で **groupItems を参照する箇所**で、`groupItemsMap[groupId]` が取れない場合に **正規化キー**（`normalizeIdForMatch`）でキー照合する（商品グループ名の Map と同様）。

## 39 グループ・約 5600 SKU でアプリタイルが遅くなる要因と改善策（2026-02）

### 事象

棚卸IDを「39 グループ・合計約 5600 SKU」のような大規模な条件で開いたとき、POS の棚卸タイルの表示や操作が遅くなる。

### 要因

#### 1. タイルを開いた直後（棚卸一覧の表示）

- **readInventoryCounts()** で、全棚卸IDが入った **1 本のメタフィールド** を取得している。
- その JSON の中に、39 グループ・約 5600 件の `groupItems` や `items` が含まれると、**レスポンスのパース** と **メモリ** の負荷が大きくなる。
- さらに **readInventoryCounts() の内部で readProductGroups()** を呼んで完了判定しているため、**メタフィールド取得が 2 回**（棚卸一覧用 ＋ 商品グループ一覧用）発生する。
- 結果として「タイルを開く → 一覧が出るまで」が遅くなりやすい。

#### 2. 棚卸IDを選んで「まとめて表示」にしたとき（商品リストの読み込み）

- **まとめて表示**では、**39 グループを for ループで 1 グループずつ**処理している（`InventoryCountList.jsx`）。
- 各グループごとに **fetchProductsByGroups([groupId], ...)** を 1 回ずつ呼ぶため、**合計 39 回** の fetch が **直列** で実行される。
- 1 回の **fetchProductsByGroups** の中身（1 グループあたり約 144 SKU と仮定）:
  - **inventoryItemIdsByGroup** がある場合:  
    - `nodes(ids: [inventoryItemId...])` を **50 件ずつ** のバッチで実行 → 約 3 バッチ（約 144÷50）。  
    - 続けて **在庫数取得** のため **getCurrentQuantity** を 1 バリアントずつ（内部で 15 件ずつまとめて）実行 → 約 10 バッチ（約 144÷15）。  
  - つまり **1 グループあたり 約 13 ラウンド** の GraphQL 通信。
- 39 グループ × 約 13 ラウンド ≒ **約 500 回以上の GraphQL** が、**直列** で発生する。
- **getCurrentQuantity** は 1 バリアントごとに 1 クエリなので、5600 SKU なら **5600 回** の在庫取得が、バッチ単位で順番に実行される。
- 加えて **完了済みグループ** では、表示用に **fetchProductsByGroups** で商品情報＋画像を取得し、予定外商品では **resolveVariantByCode** も呼ばれるため、**通信と処理がさらに増える**。
- まとめると:
  - **グループ単位の直列処理**（39 回の fetch が待ち合わせ）。
  - **在庫数取得の回数が非常に多い**（SKU 数と同じオーダー）。
  - **バッチ間の待機がない**ため、レート制限やネットワーク負荷で遅延・失敗しやすい。

#### 3. その他

- **GraphQL のタイムアウト** が 20 秒（`stocktakeApi.js`）のため、1 グループの処理が長引くとタイムアウトし、そのグループだけ「商品がありません」になることがある。
- **UI がブロックされる**：`loadProducts` が終わるまでローディングのままになり、**非同期で段階表示**していないため体感が重い。

### 改善策（実装の方向性）

| 優先度 | 内容 | 説明 |
|--------|------|------|
| **高** | **まとめて表示の「初期表示は先頭 N 件だけ」** | 全 39 グループを一気に読まず、**最初は先頭 1〜3 グループ分だけ** fetchProductsByGroups で取得して表示。残りは「さらに読み込む」やスクロールで遅延読み込みする。 |
| **高** | **在庫数の一括取得 API の利用** | getCurrentQuantity を 1 バリアント 1 回ではなく、**inventoryItemIds のリストを渡して在庫レベルを一括取得**する API（例: inventoryItem の inventoryLevels を複数まとめて取得）があれば利用し、ラウンド数を減らす。 |
| **中** | **nodes(ids) の並列化** | 1 グループ内の 50 件バッチを **直列** ではなく、**2〜3 バッチずつ並列** で実行する（レート制限に注意しつつ）。 |
| **中** | **バッチ間の短い待機** | 管理画面の get_incomplete_group_products と同様、**バッチごとに 80〜120ms の待機** を入れてレート制限を避け、失敗を減らす。 |
| **中** | **段階的表示（ストリーミング表示）** | 1 グループ読み終わるごとに **そのグループ分だけ lines に追加して setState** し、**全グループ読み終わるまで待たずに** 順次表示する。体感速度が上がる。 |
| **低** | **readInventoryCounts の軽量化** | 棚卸一覧用には **groupItems / items の詳細を返さない** オプションを用意する（別メタフィールドや「一覧用」の短い形式）。タイル起動時のパース負荷を減らす。 |
| **低** | **商品グループのキャッシュ** | readProductGroups の結果をタイル内で保持し、**同じセッションで readInventoryCounts が再度 readProductGroups を呼ばない**ようにする（既に cachedProductGroups で 1 回にしているが、一覧表示時も共通化できるか検討）。 |

### 運用でできること

- **グループ数を減らす**：可能なら 1 回の棚卸IDは **30 グループ以内** にし、それ以上は複数 ID に分ける（管理画面の「30 グループ上限」と同様の考え方）。
- **「商品グループごとに表示」で使う**：まとめて表示を使わず、**必要なグループだけ** 選んで開くと、その 1 グループ分の通信だけになり、体感が軽くなる。
- **画像をオフにする**：設定で画像表示をオフにすると、fetch 時の `includeImages` が不要になり、クエリが軽くなる。
