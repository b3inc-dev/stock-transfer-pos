# 棚卸アプリタイル：単一グループ・まとめて表示の読み込みが遅い要因

## 3つの表示モードの違い

| モード | 説明 | 初回表示時のAPI呼び出し |
|--------|------|--------------------------|
| **商品グループごとに表示** | グループ一覧を表示し、ユーザーが「読込」を押したグループだけ商品を取得 | **読込ボタンを押したときだけ** その1グループ分の `fetchProductsByGroups` を1回実行。開いた直後は商品取得なし。 |
| **単一グループ** | 1つの棚卸IDに1グループだけ紐づいている、または「1つだけ選択して表示」している | 画面を開くと **1回** `fetchProductsByGroups(1グループ)` + その後バックグラウンドで `getCurrentQuantitiesBulk`（在庫数・50件ずつ）。 |
| **まとめて表示** | 複数グループを一覧でまとめて表示 | 画面を開くと **完了/キャンセル済みグループの数だけ**、グループごとに **直列で** `fetchProductsByGroups([そのグループ])` を実行。 |

---

## 遅くなる主な要因

### 1. まとめて表示が遅い理由

- **完了済み・キャンセル済みグループごとに 1 回ずつ** `fetchProductsByGroups([groupId], ...)` を **for ループで直列実行** している（`InventoryCountList.jsx` の 1055–1181 行付近）。
- 例: 10 グループあれば 10 回の API 呼び出しが **待ち合わせ** で実行されるため、合計時間が伸びる。
- 各呼び出しで商品情報（必要なら画像付き）を取得しており、1 回あたりも重くなりやすい。

### 2. 単一グループが遅く感じる理由

- 呼び出しは **1 回** だが、次の要因で体感が遅くなりうる。
  - **商品数が多い**: `productFirst` / `limit` で 250〜600 件などを一括取得。件数が多いほど GraphQL の処理・転送が重い。
  - **画像付き取得**: `includeImages: true` で画像 URL も取得しており、ペイロードが大きい。
  - **在庫数のバックグラウンド取得**: 商品リスト表示後に `getCurrentQuantitiesBulk` を 50 件ずつ実行。件数が多いとリクエスト回数が増え、在庫表示が揃うまで時間がかかる。

### 3. グループごとに表示が相対的に速い理由

- 開いた直後は **商品の API は呼ばない**。グループ名・ステータスなど軽い情報だけ表示。
- ユーザーが「読込」を押した **1 グループ分だけ** `fetchProductsByGroups` を 1 回実行するため、「1 アクション = 1 回の取得」で済む。
- まとめて表示のように「全グループを自動で直列取得」しないため、初回表示が軽い。

## まとめ

| 比較 | 理由 |
|------|------|
| **まとめて表示** が遅い | 完了/キャンセル済みの **全グループをループで直列に** `fetchProductsByGroups` しているため、グループ数に比例して時間が増える。 |
| **単一グループ** が遅く感じる場合 | 1 回の取得で **商品数・画像・在庫取得** がまとめて重いため。グループごとに表示は「1 グループずつ・必要なときだけ」なので軽い。 |
| **グループごとに表示** が速い | 開いた時は商品取得をせず、「読込」を押したグループだけ 1 回取得する設計のため。 |

---

## 実装した改善（対応済み）

1. **単一グループを「グループごとに表示」と同じ処理に統一**
   - 単一グループでも `readProductGroups()` を1回実行し、`cachedProductGroups` を渡して `fetchProductsByGroups([その1グループ], ...)` を1回だけ実行する形に変更。
   - オプションを `productFirst: 250`, `limit: 2000`, `includeImages: showImages && !liteMode` に揃え、グループごと表示の「読込」時と同じパスにした。
   - 在庫数は従来どおり `getCurrentQuantitiesBulk` でバックグラウンド取得（1グループ分なので負荷は小さい）。

2. **まとめて表示を並列取得に変更**
   - 従来の「for ループでグループごとに直列で fetch」をやめ、`Promise.all(targetProductGroupIds.map(processOneGroupInBulk))` で全グループを並列に取得するように変更。
   - 各グループの「完了/キャンセル時の商品取得＋行組み立て」もグループ単位で並列に実行されるため、グループ数が多くても待ち時間が直列時より短くなる。
   - 非同期 I/O の並列実行のため UI スレッドをブロックせず、フリーズの心配はない。

---

## 管理画面（Admin）の未完了グループ読み込みの並列化（対応済み）

- **課題**: モーダルを開いたとき、未完了グループの商品リストを「1グループずつ順次」`get_incomplete_group_products` で取得しており、グループ数に比例して待ち時間が長くなっていた。
- **対応**: クライアントで **3 本の useFetcher** を使い、先頭 3 グループを同時に送信。いずれかが完了したらキューから次のグループをその fetcher に割り当て、最大 3 リクエストが並列に飛ぶようにした。
- **効果**: 同じサーバー・同じ API のまま、初回表示がおおむね「直列 N 回」から「並列 3 本＋キュー」になり、体感が短くなる。さらに読み込む（offset 指定）は従来どおり 1 fetcher で実施。
