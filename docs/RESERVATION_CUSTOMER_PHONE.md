# 取置受付から顧客へ電話番号を登録する

電話未登録の既存顧客を選んだ受付画面で、連絡先を入力し「顧客情報にも登録する」を明示的に選ぶ。番号を編集したとき、選択顧客が変わったときは選択を解除する。ゲスト・既存電話あり・更新権限未承認のときは顧客更新を選べない。番号は取置の補助連絡先としても維持する。

## 権限

自社・公開とも `write_customers` を任意権限として宣言する。管理画面「取置 → 設定」の顧客情報登録専用ボタンから、ストア管理者が承認する。通常取置の読取権限とは分離し、更新権限がなくても取置の連絡先を保存できる。

サーバーは署名済POS利用者、契約、許可店舗、連絡先権限、実際のインストールの `write_customers` を確認する。リクエストのcustomerIdや電話番号で登録済み取置の更新先を差し替えない。SMS・メールのマーケティング同意は変更しない。

公開版は別途Shopifyの保護対象顧客データの要件を満たす必要がある。設定ファイルへのスコープ追加や店舗の承認だけで、Shopifyのデータ利用承認が完了したとは扱わない。

## 再実行と部分成功

登録希望は取置の `customerPhoneSaveState` で永続化し、顧客・電話・取置UUIDへの同意を既存requestHashと併せて固定する。登録送信前にPOS下書きへ正確なpayloadを保存する。電話登録は在庫確保成功後の別処理とし、顧客更新失敗でも取置を再登録しない。

| 状態 | 意味・次の処理 |
| --- | --- |
| NULL | 登録希望なし。旧取置もこの状態 |
| pending | 登録希望あり、まだ書込み未実行 |
| saving | DBの条件付き更新で処理権を確保済み。別リクエストは読取確認だけ |
| saved | 更新レスポンスまたは顧客再読取で、同じ番号と確認済み |
| failed | Shopifyの明示的な入力エラー。再操作時は必ず番号を読み直してから更新 |
| unknown | 通信・保存途中失敗などで成功不明。再送せず読取確認だけ |
| conflict | 顧客に異なる番号が存在。上書きしない |

customerUpdateにはidと電話番号だけを送る。国内10〜11桁は+81へ正規化し、同じ電話の国内表記・国際表記を比較する。読取用のHTTP自動retryをmutationに使わない。タイムアウト後やプロセス停止後に、空電話の読取だけを根拠として同じmutationを再送しない。成功不明が解消しない場合はPOSの顧客情報で確認する。

状態変更と日本語の対応履歴を同一DBトランザクションで記録する。電話番号、顧客APIのrawエラー、mutation入力は履歴やログへ複製しない。電話登録の状態更新で在庫処理のversionを進めない。匿名化済み・キャンセル済み取置からは登録しない。

## 同時編集の制約

使用中のShopify API 2026-01のcustomerUpdateには「電話番号が空欄の場合のみ」の原子的条件がない。DBの条件付き更新は自アプリの並行送信を抑止する。保存直前にも顧客番号を確認するが、他アプリや管理画面が最後の読取とmutationの間に更新した番号を上書きする狭い競合窓は残る。受付画面には他端末で同時編集しない旨を案内する。既存番号を絶対に上書きしないとは保証しない。

## 関連する確認

UIは既存の固定上部・本文スクロール・固定下部と同じ部品を維持する。最初の受付画面に下部「戻る」「閉じる」は置かず、終了は左上のネイティブ×を使う。商品の確認は既存確定モーダルで行い、電話登録の選択も表示する。結果はPOS・管理画面詳細に表示する。
