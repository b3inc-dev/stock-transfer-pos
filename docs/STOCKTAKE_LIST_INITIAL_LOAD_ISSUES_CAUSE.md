# 棚卸アプリタイル：棚卸ID一覧の初回読み込み設定による不具合の要因

## 現象（3点）

1. **① 一括読み込みより逆に遅くなった**
2. **② 設定100件なのに棚卸IDが20件程度しかないのに一度で全件読めず、「未読み込み」の読込ボタンを押さないと過去分が表示されない**
3. **③ ロケーションが不明のリストが発生し、対象ロケーション以外に「不明」のリストが多く表示される**

---

## 要因

### ① 読み込みが遅くなった要因

- **`getStocktakeListLimit()` の追加**
  - 初回表示件数を設定値（`outbound.historyInitialLimit`）で決めるため、`readInventoryCountsFirstPage()` 内で `getStocktakeListLimit()` を呼ぶようになった。
  - `getStocktakeListLimit()` は内部で **`fetchSettings()`** を呼び、メタフィールド（設定）の取得が **1回増えている**。
- 以前の一括読み込みでは、この設定取得が初回の棚卸ID一覧取得経路に入っていなかった可能性が高く、**設定読み込みの1往復分**だけ遅くなっている。

**該当コード（stocktakeApi.js）**

- `readInventoryCountsFirstPage()` の `Promise.all` に `getStocktakeListLimit()` が含まれる（352–356行付近）。
- `getStocktakeListLimit()`（319–323行付近）が `fetchSettings()` を呼んでいる。

---

### ② 全件（例: 20件）が一度に表示されない要因

- **「初回」＝「最後の1チャンクだけ」になっている**
  - `readInventoryCountsFirstPage()` は、チャンク分割されている場合に **「先頭ページ」＝「いちばん新しいチャンク（last chunk）1本だけ」** を読んでいる。
  - その1チャンク内の件数に `listLimit`（例: 100）をかけた `counts.slice(0, listLimit)` しか返していない。
- つまり **「全チャンクをまたいで先頭 listLimit 件」ではなく、「最後のチャンク内の先頭 listLimit 件」** だけが初回で返る。

例:

- 棚卸IDが 20 件で、チャンクが 2 つ（例: 1チャンク目に5件、2チャンク目に15件）に分かれている場合  
  → 初回は「2チャンク目」だけを読むため **15件しか返らず、1チャンク目の5件は「未読み込み」の読込ボタンでないと表示されない**。
- 設定が 100 件でも、**「100件まで」は「最後の1チャンク内」に限定**されているため、20件全体が複数チャンクに分かれていれば全件は初回に出ない。

**該当コード（stocktakeApi.js）**

- `useListMetafield === true` の場合（373–395行付近）:
  - `firstChunkIndex = totalChunks - 1` で **最後のチャンクのみ** 取得。
  - `counts = chunk` に対して `counts.slice(0, listLimit)` で返している。
- メインのチャンク利用時（424–448行付近）も同様に、`firstChunkIndex = totalChunks - 1` で最後の1チャンクだけ取得し、`counts.slice(0, listLimit)` で返している。

→ **「初回で listLimit 件まで表示」の意図は「全チャンクをまたいで先頭 listLimit 件」であるべきところが、「最後の1チャンク内の先頭 listLimit 件」という実装になっている。**

---

### ③ ロケーションが不明のリストが多く出る要因

- **ロケーション絞り込み時の「locationId なし」の扱い**
  - `InventoryCountConditions.jsx` の `filterByLocation` で、`locationId` が **null または空** の棚卸は **「対象ロケーションに一致する」とみなして true を返し、リストに含めている**。
- その結果、対象ロケーションで絞り込みをしていても、
  - `locationId` が入っていない（古いデータや保存不備など）棚卸がリストに混ざる。
  - 表示時には `locationNames.get(c.locationId)` が取れず **「ロケーション不明」や「－」** として表示される。
- さらに、初回が「最後の1チャンクだけ」のため、そのチャンクに他ロケーションや locationId 未設定のデータが含まれていると、**「対象ロケーション以外に不明のリストが多く出る」** ように見える。

**該当コード（InventoryCountConditions.jsx 127–137行付近）**

```javascript
const filterByLocation = useCallback((list, locGid) => {
  // ...
  return list.filter((c) => {
    const cid = c.locationId;
    if (cid == null || cid === "") return true;   // ← ここで locationId なしを「表示する」扱いにしている
    // ...
  });
}, []);
```

→ **ロケーションで絞り込んでいる場合は、`locationId` が null/空の棚卸は「対象外」として除外する方が妥当。**

---

## まとめ

| 現象 | 主な要因 |
|------|-----------|
| ① 遅くなった | 初回取得経路に `getStocktakeListLimit()` → `fetchSettings()` が入り、設定取得が1回増えたため。 |
| ② 20件なのに全件一度に出ない | 「初回」が「最後の1チャンクだけ」の取得になっており、「全チャンクをまたいで listLimit 件」を返していないため。 |
| ③ ロケーション不明が多い | ロケーション絞り込み時でも `locationId` が null/空の棚卸を「一致」として含めており、それらが「不明」として表示されるため。 |

修正する場合は、

- ②: 初回で「最後の1チャンク」に限定せず、**必要なだけチャンクを読んで合計 listLimit 件（または全チャンク）を返す**ように変更する。
- ③: **ロケーション指定時は `locationId` が null/空の棚卸を filterByLocation で除外する**（`return false`）ようにする。
- ①: **設定のキャッシュや、初回の並列化・取得タイミングの見直し**で、`fetchSettings()` の影響を減らす。

といった対応が考えられます。

## 追記：確認事項への回答

### ① チャンクで対象全件読み込みにしたとき、読み込みスピードはどのくらい遅くなるか

- **遅くなる分の目安**: **（読むチャンク数 − 1）× 1チャンクあたりの応答時間**
- 1チャンクの取得は GraphQL のメタフィールド1件取得なので、ネットワークや Shopify の応答次第で **おおよそ 100〜400ms/回** 程度が目安（環境により前後します）。
- 例:
  - チャンクが **2本** で初回に2本とも読む場合: 1本だけ読むときより **約 100〜400ms 遅い**。
  - チャンクが **5本** で listLimit に達するまで5本読む場合: 1本だけのときより **約 400ms〜1.5秒程度遅い**。
- チャンク数が少ない（例: 2〜3本）うちは体感差は小さく、4〜5本以上になると「少し遅い」と感じる可能性があります。  
  一方で、**初回から listLimit 件まで揃う**ので、「未読み込み」を押す回数は減り、トータルでの操作時間が短くなる場合もあります。

---

### ③ そもそもなぜロケーションが読めず「不明」になるか

表示で「ロケーション不明」や「－」になるのは、`locationNames.get(c.locationId)` や `getLocationName(c.locationId)` で名前が取れないときです。主な要因は次のとおりです。

1. **保存されている棚卸に `locationId` がない**
   - 一覧用 list チャンクは `toMinimalCountForList(c)` で `c.locationId` をそのまま保存している。
   - 過去の仕様や不具合で **`locationId` が付かずに保存されたデータ**（レガシーや別経路で作られた棚卸）があると、その棚卸は「ロケーション不明」になる。
   - 管理画面で新規作成する棚卸は `locationId` を必ず持って保存されるため、新規分だけなら通常は発生しない。

2. **`locationId` の形式と `getLocationName` の照合が一致していない**
   - POS 側では `locationId` に **数値だけ**（例: `"123"`）や **GID**（例: `"gid://shopify/Location/123"`）のどちらかが入っている可能性がある。
   - `getLocationName(locationId)` は `fetchLocations()` の結果に対して **`locations.find((l) => l.id === locationId)`** で検索している（厳密一致）。
   - Shopify の GraphQL は `locations.nodes[].id` に **GID** を返すため、保存されているのが数値だけの `"123"` だと `l.id === "123"` は成立せず、**名前が取れず「不明」** になる。

3. **そのロケーションが一覧に含まれていない**
   - `fetchLocations()` は権限やストア設定により、**一部のロケーションしか返さない**ことがある。
   - 削除済みや非表示のロケーションに紐づく棚卸は、`locationId` が正しくても名前解決できず「不明」になる。

4. **取得時のエラー**
   - `fetchLocations()` や GraphQL が失敗すると `getLocationName` は `null` を返し、表示は「－」などになる。

**まとめ**: 「不明」の多くは、**(A) 保存データに `locationId` がない** か **(B) `locationId` が数値のみで、getLocationName の GID との厳密一致で弾かれている** のどちらかが原因と考えられます。  
③の対策として「ロケーション指定時は `locationId` が null/空の棚卸を一覧に出さない」ようにしたことで、(A) のケースは対象ロケーションの一覧からは消えます。  
(B) を減らすには、`getLocationName` 内で **数値と GID の両方で検索する**（例: `locationId` が数値のときは `gid://shopify/Location/${locationId}` も試す）といった正規化を入れる方法があります。

## 追記2：追加の確認事項への回答

### ① チャンクよりシンプルに全て読み込んだ方が早い？チャンクを使わず全て読み込む場合、ID数どのくらいまで耐えれる？

- **「1回で全部読む」の方が早いか**
  - **読み取り回数だけ見れば、1回で済む方が早い**（往復が1回で終わる）。
  - ただし「チャンクを使わず全て読み込む」を実現するには、**全データを1つのメタフィールドに収める**必要がある。

- **1メタフィールドに収まる件数の目安**
  - Shopify のメタフィールド値は **API バージョンにより制限** がある（例: 2026-04 以降は **16KB** など。要公式ドキュメント確認）。
  - 現状の list 用ミニマム1件あたりの JSON は、id / locationId / status / productGroupIds 等で **おおよそ 200〜600 バイト** 程度（内容による）。
  - 16KB 制限なら **約 25〜80 件**、32KB なら **約 50〜160 件** が目安（あくまで概算）。
  - つまり **「チャンクを使わず1メタフィールドだけで全て」にすると、数十件〜百数十件程度が上限** になり、それを超えるとチャンク分割が必須。

- **まとめ**
  - **件数が少ない（目安: 数十件以内）なら**、1メタフィールドにまとめて **1回で読む方がシンプルで速い**。
  - **件数が増える（数十〜100件超）と** 1メタフィールドのサイズ制限に当たり、**チャンク分割＋複数回読み**が必須。その場合「全件」を出すには複数チャンクを読む必要があり、読み取り回数は増える。
  - 「耐えれる ID 数」は **保存形式と API のメタフィールドサイズ制限** で決まり、**おおまかに数十〜百数十件が目安**。それ以上はチャンク前提になる。

### ③ ログインしているロケーション以外は全て不明になるということ？

- **いいえ、そういう仕様ではありません。**
- ロケーション名の解決は **「ログイン中のロケーションかどうか」では判定していません**。
  - 一覧に表示される **各棚卸** について `getLocationName(count.locationId)` を呼び、**その `locationId` に対応する名前** を取得している。
  - `getLocationName` は **`fetchLocations()` で取得した「ストアのロケーション一覧」（最大250件）** から、`locationId` に一致するものを検索して名前を返している。
- したがって、**ログイン中かどうかに関係なく**、次の条件を満たせば名前は出ます。
  - その棚卸の `locationId` が **正しく保存されている**
  - `locationId` の形式が **getLocationName の検索と一致している**（例: GID なら GID 同士で比較）
  - そのロケーションが **`fetchLocations()` の結果に含まれている**（削除済みでない等）
- 「不明」になるのは、**ログイン中かどうか** ではなく、
  - `locationId` が null/空、
  - 形式の不一致（数値のみ vs GID）、
  - そのロケーションが一覧にない／取得エラー
  のいずれかが原因です。
- **結論**: ログイン中のロケーション以外がすべて不明になるわけではなく、**上記の条件が満たされていれば、他のロケーションも通常は名前表示されます**。

## 追記3：メタフィールド保存の変更とタイルのロケーション情報

### ① チャンク処理をする前と、チャンク処理を組み込んだ際でメタフィールドの保存方法を変更したか

- **はい、変更しています。**
- **チャンク導入前（または「チャンクを使わない場合」）**
  - 棚卸が **1件だけ** かつ **1件のサイズが CHUNK_BYTES（32KB）以下** のときは、**メインキー 1つ**（`inventory_counts_v1`）に **配列 1件の JSON** をそのまま保存。
  - 管理画面の `writeInventoryCountsChunked` でも、このときは **list 用メタフィールドは書いていない**（メインキーだけ更新）。
- **チャンクを組み込んだ後（複数件 or 1件でも大きい場合）**
  - **メイン側**: メインキーには **descriptor**（`_chunked: true`, `totalChunks`）だけを保存し、実データは **メインチャンク**（`inventory_counts_v1_c0`, `_c1`, …）に分割して保存。
  - **一覧用**: **list 用キー**（`inventory_counts_list_v1`）に list 用 descriptor を保存し、実データは **list チャンク**（`inventory_counts_list_v1_c0`, …）に保存。あわせて **棚卸ID→チャンク番号のインデックス**（`inventory_count_index_v1`）も保存。
- つまり「チャンク処理を組み込んだ際」に、
  - メインは「配列 1本」から「descriptor ＋ チャンク群」に変わり、
  - **一覧用の list キー ＋ list チャンク** という **新しい保存形式を追加** しています。**保存方法は変更・拡張している** という理解でよいです。

### ③ アプリの棚卸タイル側にロケーション情報がないから、自ロケーション以外は不明になるのでは？

- **コード上の仕様**
  - タイル側では `getLocationName(count.locationId)` で名前を解決しており、その中で **`fetchLocations()`** を呼んでいます。
  - `fetchLocations()` は **`locations(first: 250)`** で **最大 250 件のロケーション** を取得する実装なので、**「タイル側にロケーション情報がない」のではなく、一覧用に複数ロケーションを取得する想定** になっています。
- **そのうえで**
  - 通常の Admin API では `locations` は **ストアのアクティブなロケーション一覧** を返す仕様です。
  - 一方で、**POS アプリの実行環境**（どの API / トークンで叩いているか）や **アプリの権限** によっては、**返却されるのが「ログイン中ロケーションのみ」に制限されている** 可能性はあります。
- **その場合**
  - タイルから見ると「取得できたロケーション情報が自ロケーション分だけ」となり、**他ロケーションの棚卸は `locationId` が一致せず名前解決できず「不明」になる**、という動きになります。
- **結論**
  - **「タイル側にロケーション情報がないから自ロケーション以外は不明」という理解は、あり得る説明です。**  
  - コード上は「全ロケーション取得」のつもりで `locations(first: 250)` を叩いていますが、**POS 環境や権限の都合で自ロケーションしか返ってこない場合は、ご認識のとおり自ロケーション以外は不明になります。**  
  - 逆に、同じ `locations` で複数ロケーションが返る環境では、`locationId` の形式さえ合っていれば他ロケーションも名前表示されます。
