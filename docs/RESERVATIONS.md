# 取置（Issue #59）— 要件・状態遷移・検証

2026-11-25。Codex。ユーザーの実装依頼で着手。管理画面は UI_RULES v1.1 の共通部品、POS はロス画面を基準とする。

## 初回仕様

自店舗の在庫追跡バリエーションを最大250明細、正の整数で確保する。複数明細は1回の inventoryMoveQuantities で動かす。顧客はPOSカートで選択、ゲストは氏名・電話必須。標準日数は全店共通（初期7日、1〜365）。登録時の店舗現地日付にN日を足した日を期限として固定する。現地日付はサーバーに設定した店舗のIANAタイムゾーンを保存する。日付の変わり目から要対応とする（営業時間マスタがないため開店時の通知はPOS起動時）。期限だけでは解除しない。

不通は要対応のまま、来店予定は未来の次回確認日まで要対応から外す。一覧は自店舗・要対応/取置中/終了、番号・氏名検索、電話マスク。詳細の連絡先は署名済みPOSトークンのショップとsubがRESERVATION_POS_ACCESSで店舗・連絡先参照を許可されている場合のみ表示する。pinned staff の申告を権限判定に使わない。担当の記録は署名済みsub。既存顧客の氏名・電話はShopifyから取得し、DBには顧客IDと取置用の補完電話だけを保存する。ゲスト連絡先は専用DBのみに保存し、終了後に管理画面で匿名化可能。通知・在庫履歴・注文・印刷に氏名/電話を入れない。

レシートの暫定値: 発行しないが既定、対面でのみ選択、お客様控え1枚、固定HTML、店舗・番号・登録日・期限・明細・担当ID。氏名・電話・金額なし。保存と印刷を分離し何度でも再印刷する。2026-07 の新拡張だけ shopify.printing を使う。

## 在庫と状態

`reserving → held → checkout → completing → sold`、`held → cancelling → cancelled`。
Shopifyの結果不明時は同じpending状態で「確認中」、明確な拒否は直前状態へ戻す（登録拒否はfailed）。DBに操作ID・完全な入力・開始時刻を送信前に永続化。同じ操作の再送は同じ @idempotent key と同じ入力。DB version CASで販売と解除を排他。23時間以上たった結果不明操作は自動再送せず、管理者の照合が必要。既存Transfer/apply-change/履歴の冪等性と混同しない。

確保 available→reserved、キャンセル reserved→available。同一店舗の両状態を読んでchangeFromQuantityでCASする。最後の1点の並行確保は片方を拒否。250超を暗黙に分割しない。

会計に入る前に確保を解除しない。空で顧客が一致するカートだけに、取置番号とランダムな会計キー、商品を渡す。空カートへ会計キーを書いてからサーバーの会計状態を確定するため、その応答が失われても同じキーで再開できる。確かな拒否時だけ、同じ空カートのキーを取り除く。サーバー応答待ちでカートが切り替わった場合は顧客・商品を変更する前に停止する。同じ会計キーのカートは数量を照合して不足分だけ補い、別人・別取置のカートは停止。会計中断でもreservedは維持。決済済みPOS注文の店舗・顧客・全対象バリエーション数量・取置番号/会計キー・キャンセル/返品/明細ページ終端をサーバーで照合してからreserved→availableを1回行う。注文の通常減算と合わせて A5/R0/O5→A3/R2/O5→（POS販売）A1/R2/O3→A3/R0/O3。**この順番・棚卸との競合は実機合格必須**。拡張はPOSの在庫不足販売を強制できないため、スタッフが警告を確認する。

会計へ渡した後のキャンセルは初回は安全側に止める。会計キーが付いたカートから何度でも再開できる。カートが消えた場合に新しいカートを自動作成すると未着注文と二重会計になるため止め、注文番号で照合する。会計失敗後に新カートへ戻す操作は、実機で注文不在の確定方法を確認するまで解放しない（初回受入の未完了項目）。

## 開発環境の有効化・権限設定

本番では実行しない。開発用DBへmigrationを適用したあと、次を開発サーバーにだけ設定する。

```dotenv
RESERVATIONS_ENABLED=1
# ショップ → 署名済みトークンsub（ログインユーザー） → 店舗と連絡先参照権限
RESERVATION_POS_ACCESS={"example.myshopify.com":{"123":{"locations":["gid://shopify/Location/456"],"contact":true}}}
# 店舗の現地日付は端末設定に依存させない。IANA名を店舗ごとに固定する。
RESERVATION_LOCATION_TIMEZONES={"example.myshopify.com":{"gid://shopify/Location/456":"Asia/Tokyo"}}
```

上記IDは非secretの例。実トークンを設定・ログへ書かない。権限のないアカウント・店舗はAPIで403となる。連絡先権限は**ログインアカウント単位**であり、POSのPINだけを入れたスタッフ単位の権限ではない。PIN交代で連絡先を分離する運用は未対応。権限を持つログインアカウントを共有しないこと。担当欄は署名済みユーザーと、POSから申告された数値staffMemberIdを併記する（後者は署名済みの本人証明ではない）。

管理画面の「取置」から、ストア管理者が任意scope（read_orders/read_customers）を許可する。公開アプリは保護顧客データ承認後にのみ配備する。既存の必須scopeは変更しない。許可前にPOSで在庫操作を行わない。

顧客データ開示Webhookは専用DBに依頼IDと顧客IDだけを耐久受付する。管理画面に未処理依頼を表示し、通常のブラウザPOSTでJSONをダウンロードする。配送成功を判定できないため、開示依頼は再ダウンロードできるまま残す。顧客データ画面とダウンロードは、機能無効化・Pro解約・ロケーションプラン不一致後も認証済み管理者から利用できる。ストア担当者が本人確認と提供を行う。customers/redactは取置の連絡先・顧客IDを匿名化し、在庫と状態は維持。shop/redactは公開用・未再インストールの従来条件に従って取置・イベント・設定・開示依頼を削除する。

## 商品詳細からの登録（2026-11-25 Tさん依頼）

## スタッフの操作の流れ（有効化・配備後）

1. 管理画面の「取置」→「期限を設定」で標準取置日数を保存する。既存顧客なら、先にPOSで顧客を選ぶ。
2. 商品詳細で種類を選び、アクションメニューの「取置する」を押す。対象商品が数量1で入る。ホームの「取置」タイル→「取置を登録」→検索/バーコードからも登録できる。
3. 数量と顧客・連絡先を確認する。ゲストは氏名・電話番号を入力する。必要なら商品を追加し、対面なら取置レシートの発行を選ぶ。
4. 「確保して登録」を押す。成功画面の取置番号と受取期限を確認して、現物を取置棚へ移す。印刷が失敗した場合も登録は残り、詳細から再印刷できる。
5. ホームのタイルの「要対応 ○件」から自店舗の取置を確認する。電話後は「不通を記録」、または次回確認日を入れて「来店予定を記録」。期限だけで自動解除しない。
6. 来店時は取置の詳細→「カートへ追加」。同じ店舗の空のカート、または同じ取置の会計用カートへ商品と数量を渡す。POSの通常カートを開いて支払う。支払済み・全数履行済みの注文と内容が合った時点で販売完了になる。自動照合が進まない場合は詳細の「注文を探す」から決済後の注文を照合する。
7. 来店前に取り消す場合は、詳細→「取置をキャンセル」→商品・数量を確認→「解除を確定」。在庫を1回だけ販売可能数へ戻す。

会計へ渡した後の取り消し、新しいカートへの復旧、PINごとの連絡先権限は、上記の未完了事項が残る。今回の追加も本番未配備・実機未確認で、今すぐ店舗で利用できる状態とは区別する。

## 管理画面の構成（2026-11-25更新）

上位メニューは「取置」にまとめ、内部に「設定・顧客データ・履歴」の移動メニューを設置する。設定は標準取置日数と顧客/注文の任意権限確認・許可、顧客データは開示依頼と終了した取置の連絡先削除、履歴は共通History-tableで受付日時・店舗・期限・状態と詳細へのリンクを表示する。取置履歴と詳細の在庫操作は従来どおりPOSで行う。

顧客データの入口は `/app/reservations/customer-data`。旧 `/app/reservation-privacy` と開示ダウンロード用POST `/app/reservations/privacy` を維持し、プラン・機能スイッチに関係なく開示/削除へアクセスできる。通常の取置利用ができないプランでは上位の「取置」から顧客データへ直接進む。

Shopifyの必須scopeでインストール時の許可を求める方式も可能。ただし全店舗が対象となり、公開版では保護顧客データ承認は別途必要。今回はD18/D20の任意scope方針を維持し、必須権限は変更していない。

## ロス画面を参考にしたUIの見直し（2026-11-25）

POSはロスの固定領域と本文スクロールを参考に、受付条件→商品選択→確認→登録の流れとする。検索・受取期限の年月日/今日・状態の等分ボタン・更新時刻は上の固定領域、履歴行は中央、店舗と戻る/主操作は固定フッターに置く。解除は独立した確認画面を1回だけ表示する。主ボタンは右下に1つ、完了済み詳細の左下は閉じる。既存の登録番号再利用・下書き保存・カート照合・会計後の在庫処理は維持する。日付絞り込みはページ分割前にサーバーで行い、「今日」は設定済み店舗の現地日付を使う。更新時刻はJST。件数のある取置タイルは引き続き要対応件数を表示する。

管理画面の履歴は添付のロス画像に合わせ、左が店舗/状態の複数選択と日時ソート、右が件数と取置ごとの行（店舗・期限・状態・明細数・合計点数）。25件でページ送りし、絞り込みと並び順を詳細から戻った時も保持する。サブメニューは棚卸を参考に下線区切り・選択中の灰色背景とする。自社用ホームは9.取置設定、10.POSアプリタイル追加。公開版は既存の料金プラン手順による連番に従う。取置が無効なら設定への入口を出さない。

### 商品検索・商品行・カメラスキャンの追補

商品名/SKU/JANの検索クエリ生成をロスと共通の `extensions/common/variantSearch.js` にまとめる。1文字から300ms待って検索し、設定の検索初回件数（10〜50）と商品表示件数を使う。検索の追加読込と表示ページ送りは分け、遅れて返った前の検索結果は世代番号で破棄する。候補と追加済み商品は画像・商品名・種類・SKU/JAN・現在店舗の販売可能在庫を表示し、同一バリエーションの再追加は数量加算とする。数量の直接入力・増減・1個時の削除、画像ON/OFFを用意する。下書きや商品詳細から持ち込んだ商品も表示用情報を読み直し、数量は保持する。

商品画面のカメラと外部スキャナーは同じキューで逐次処理する。同一コード350ms未満の二重イベントを抑制し、完全一致バーコード優先、次にSKU完全一致を使う。同じコードの複数商品や候補が未取得ページに続く場合は自動追加を止め、検索結果から選ぶ。画面移動時は同期的にキューを停止し、カメラを閉じ、世代を更新する。遅れた結果で別画面の下書きを変えない。

検証: 関連64テスト、SDK5コンテキスト、対象lint/build。ローカルDOMで実コンポーネントの商品名・種類・SKU/JAN・画像・在庫、候補の連続追加、追加済み数量減算、カメラAPI呼出し、スキャン通信待ち中の戻る操作と遅延応答の非追加を確認した。これはネイティブPOSの実機レイアウト・カメラ映像・印刷の確認を代替しない。

## 取置レシート編集と2種類の控え（2026-11-25）

従来の固定HTML・1枚という暫定仕様を、本節で置き換える。取置のサブメニューに「レシート編集」を追加する。POS Receiptのテンプレート設定・印字プレビューの実装を参考に、テンプレート名、HTTPSロゴ、店舗/発行者情報、受付日/店舗名/担当/SKU/JANの表示、58/80mm、文字サイズ、見出しの揃え、ロゴ/店舗情報の位置、本文間隔、タイトル/末尾メッセージを編集する。店舗ごとではなくアプリ導入ストア内で共通設定。取置番号・受取期限・商品/数量は必須表示、顧客氏名/電話・金額は印字しない。SKU/JANはこの追加以降の登録でサーバーが取得・保存した値を使い、旧明細は空欄とする。

「お客様お渡し用」「店舗保管用」を管理画面で選ぶ。初期値は両方、片方だけにも設定できる。最低1種類を選ぶ。印刷しない受付では既存のPOSの発行スイッチをOFFにする。各控えには用途のラベルを付ける。両方の場合は改ページCSS付きの2ページHTMLを1つの印刷ジョブで送る。これはShopifyの印刷チュートリアルの複数文書方式によるもので、プリンターの紙送り・自動カット・実寸は未確認。ジョブ送信は物理印刷完了を意味しない。

プレビューとPOSの認証済み印刷URLは同じ `renderReservationReceipt` を使用し、印刷時に保存済み設定を読み取る。設定はStockReservationSettingsのreceiptLayoutとreceiptVersionに保存し、日数設定は上書きしない。設定更新はバージョン比較で競合を拒否し、失敗時にフォームの内容を保持する。ロゴURLはHTTPS、自由入力はHTMLエスケープ、プレビューはsandbox、HTMLはCSPでスクリプトを禁止する。

## 追加画像に合わせたPOS表示の修正（2026-11-25）

受付時にsessionDisplayを読み、店舗名とPOSカートの選択済み顧客を表示する。カートの顧客は購読し、切替時に同期で世代を無効化して古い氏名/電話を表示しない。店舗名だけの表示は署名済みPOS利用者に許し、顧客表示には従来の店舗利用許可、電話全文にはcontact許可を要求する。sessionDisplayは在庫や取置を操作しない。他コマンドの許可条件は変えない。権限不足は理由を文字で表示し、権限を推測で付与しない。ゲストと会員の補助電話を分離し、不確実な再送payloadと編集用のゲスト電話を別に復元する。

ユーザーの画像②の追加指示により、取置では帯型アテンション（s-banner）を使わず、処理中と失敗理由をs-textで表示する。一般のPOS共有ルールにある青い読み込み帯より、この明示指示を優先する。失敗理由そのものは隠さない。

履歴検索はPOS Receiptの商品券を参考に、2文字/300msで行う。2026-11-25の追加指定により、年月日ボタン・今日・日付フィルターはPOS画面から撤去し、登録日時が古い順に表示する。状態切替はSalesSummaryModalと同じgapなし・33.33%の3等分にし、折り返しを防ぐ。ページ送りはPOS Stockの表示範囲/全件数・前へ/次への構成で本文の上に置き、25件以内の先頭ページでは出さない。サーバーで減少後のページを補正し、通信中の条件変更は最新の検索へ順番に引き継ぐ。
