# 棚卸ID一覧の初回読み込み：最適解の設計

## 結論（ご質問への回答）

- **全て改善する最適な処理**: 下記「採用した方針」のとおり。
- **「初回1チャンクだけ読む」は必須ではない**  
  設定の初回件数（listLimit）を満たすために、**初回から複数チャンクを読んで listLimit 件に達するまで（または全チャンクまで）取得する**形に変更してよい。その方が「全件が少ないときは一度で全部出る」「未読込ボタンに頼りすぎない」という意味で最適。

---

## 採用した方針（3つの不具合への対応）

### ① 読み込みが遅くなった対策

- **設定取得のキャッシュ**
  - `fetchSettings()` の結果をメモリに保持（TTL 2分）。
  - `getStocktakeListLimit()` が毎回 `fetchSettings()` を呼んでも、2回目以降はキャッシュから返すため、初回以降の体感を軽くする。
- 初回1回目の呼び出しでは依然として設定用メタフィールド1回分は発生するが、「初回1チャンクだけ」をやめたことによる追加往復の影響を、キャッシュで相殺する。

### ② 全件（例: 20件）が一度に出ない対策

- **初回で「listLimit 件に達するまで（または全チャンクまで）複数チャンクを読む」**
  - 以前: 最後の1チャンクだけ読んで `slice(0, listLimit)` していた。
  - 変更後: 新しいチャンクから順に（last chunk → その1つ前 → …）読んで **配列に積み上げ、合計が listLimit に達するか、全チャンクを読むまで** ループ。その後 `slice(0, listLimit)` して返す。
- 返却に **`loadedChunkCount`** を追加。UI は「未読み込み」の読込ボタン用に、既に読んだチャンク数として `loadedChunkCount` を使う。
- これにより「棚卸IDが20件しかないのに読込ボタンを押さないと出ない」という事象を解消。**初回1チャンクに限定する必要はない**。

### ③ ロケーションが不明のリストが出る対策

- **ロケーション指定時は locationId なしを一覧に出さない**
  - `filterByLocation` で、`locationGid` が指定されているときは **`locationId` が null または空の棚卸は「一致しない」として除外**（`return false`）。
  - 対象ロケーション以外や「不明」が多く出る原因を、データ欠損分を表示しないことで抑える。

## 処理の流れ（変更後）

1. **初回表示**
   - ディスクリプタ・商品グループ・listLimit を取得（listLimit はキャッシュ済み fetchSettings から取得することが多い）。
   - list 用メタフィールドがチャンク分割されている場合:
     - チャンクを **新しい方から順に** 読む。
     - 取得済み件数が listLimit に達するか、全チャンクを読むまで繰り返す。
   - 取得した一覧を `slice(0, listLimit)` し、`loadedChunkCount` とともに返す。
2. **「未読み込み」の読込**
   - まだ読んでいないチャンク（loadedChunkCount より前のインデックス）を、従来どおり `readInventoryCountsPage` で読んで追加。
3. **ロケーション絞り込み**
   - 一覧表示時は `filterByLocation` を通し、ロケーション指定時は `locationId` が null/空の棚卸は表示しない。

---

## 初回「1チャンクだけ」にしない理由

- 「初回は1チャンクだけ」にすると、**全件数が少ない（例: 20件）かつ複数チャンクに分かれている場合に、初回では一部しか表示されず、必ず「未読み込み」の読込が必要になる**。
- 設定の「初回読み込み件数」の意図は「最初に表示する件数の上限」であり、「最初に読むチャンク数を1にせよ」ではない。
- そのため、**初回から複数チャンクを読んで listLimit 件（または全件）を返す**形が最適で、初回1チャンクに制限する仕様は必須ではない。
