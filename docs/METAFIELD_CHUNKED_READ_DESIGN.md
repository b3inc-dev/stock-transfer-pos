# メタフィールド分割取得の設計と「表示の読み込み件数制限」

**日付**: 2026-02

---

## 1. 目的

- **読込スピードの統一**: メタフィールドを「1回で全件」取るのではなく、**分割（チャンク）で取得**し、初回表示は「先頭1チャンクだけ」にすることで、データ量に左右されにくい読込時間にする。
- **表示の読み込み件数制限**: 「初回は設定件数だけ取得して表示し、『読込』で次のチャンクを追加取得する」という処理の流れを、API と UI の両方で一貫させる。

---

## 2. ストレージ形式（v2 チャンク形式）

### 対象

- **発注** (order_request_entries)
- **仕入** (purchase_entries)
- **ロス** (loss_entries)
- **調整** (adjustment_entries)

※ 棚卸 (inventory_counts) はすでに**バイト単位**のチャンクで保存しているが、あくまで「1 value のサイズ制限」対策のため。一覧の「先頭 N 件だけ取得」とは別仕様のため、今回の「件数ベース分割取得」の対象外とする。

### 形式

- **マニフェスト用キー**（1つ）  
  - 例: `order_request_entries_v2_meta`  
  - 値: `{ "chunkSize": 100, "chunkCount": 3 }`  
  - 意味: 1チャンクあたり 100 件、チャンクが 3 個ある。

- **データ用キー**（chunkCount 個）  
  - 例: `order_request_entries_v2_0`, `order_request_entries_v2_1`, `order_request_entries_v2_2`  
  - 値: それぞれ JSON 配列（最大 chunkSize 件）。

- **チャンクサイズ**: 設定の「初回読み込み件数」と揃える（未設定時は 100）。これが **表示の読み込み件数制限** の単位になる。

### 移行（v1 → v2）

- 初回読み込み時に、v2_meta が無ければ **v1 の単一キー** を読む。
- その配列を chunkSize 件ずつに分割し、v2_meta と v2_0, v2_1, ... を書き込む。
- 以降は v2 のみ参照。v1 は上書きしない（管理画面など他で参照している可能性があるため、残しておく）。

---

## 3. API の役割分担

### 一覧表示用（読込スピードを揃えるため）

| API | 役割 | 取得量 |
|-----|------|--------|
| `readXxxFirstPage()` | 初回表示用 | **マニフェスト + 先頭1チャンクだけ**（= 設定件数まで） |
| `readXxxPage(pageIndex)` | 「読込」押下時 | **指定したチャンク1つだけ** |

- 返却: `{ entries: [...], hasMore: boolean, chunkCount?: number }` など。
- いずれも **1リクエストで 1チャンク分のデータだけ** を返すので、データ量が増えても初回・追加読込の時間が揃う。

### 更新用（全件必要なとき）

| API | 役割 | 取得量 |
|-----|------|--------|
| `readXxxFull()` | 追加・編集・削除の前に「全件」欲しいとき | 全チャンクを取得してマージした配列 |

- 例: 新規発注追加時、キャンセル時、仕入の入庫確定時など。
- 一覧では「先頭だけ／読込で追加」、更新時だけ「全件」という使い分け。

### 書き込み

| API | 役割 |
|-----|------|
| `writeXxx(entries)` | 受け取った **配列全体** を、chunkSize で分割し直して v2 のマニフェスト＋全チャンクを書き込む |

- 既存の「配列を丸ごと渡して上書き」の呼び出し方はそのまま。中でチャンク分割する。

---

## 4. 表示の際の「読み込み件数制限」の処理の流れ

### 4.1 初回表示

1. 画面表示時や「再読込」時に **`readXxxFirstPage()`** を 1 回だけ呼ぶ。
2. API は **マニフェスト + 先頭チャンク（0番）だけ** を取得し、`entries`（最大 chunkSize 件）を返す。
3. UI はその `entries` をそのまま **初回表示リスト** として表示する。
4. `hasMore` が true なら「未読み込み一覧リストがあります。（過去分）」＋「読込」ボタンを表示する。

→ ここまでで「**表示の読み込み件数制限**」＝「初回は設定件数（= 1チャンク）だけ取得して表示する」が実現する。

### 4.2 「読込」ボタン押下

1. ユーザーが「読込」を押す。
2. UI は **次のページ番号**（例: 1）で **`readXxxPage(1)`** を 1 回呼ぶ。
3. API は **そのチャンクのキーだけ** を取得し、`entries` を返す。
4. UI は既存の表示リストに **append** し、表示件数を増やす。
5. まだ `chunkCount - 1` より小さいページしか読んでいなければ、再度「読込」を表示する。

→ 「読込」1回ごとに **1チャンク分だけ** 取得するので、読込スピードがデータ量に依存しにくくなる。

### 4.3 更新処理（追加・編集・削除）のとき

1. 例: 発注を 1 件キャンセルする。
2. 一覧では「先頭＋読込で追加した分」しかメモリに無い可能性がある。
3. そのため、更新前に **`readXxxFull()`** を 1 回呼び、**全チャンクを取得してマージした全件** を取得する。
4. 取得した配列の該当件を更新し、**`writeXxx(updated)`** で書き戻す（内部でチャンク分割して保存）。

→ 表示は「件数制限付きの分割取得」、更新は「必要なときだけ全件取得」で統一される。

---

## 5. まとめ（制限がかかっている箇所）

| 段階 | 何が制限されるか | どう実現するか |
|------|-------------------|----------------|
| **初回表示** | 取得件数 | `readXxxFirstPage()` で先頭 1 チャンクだけ取得（= 設定の初回読み込み件数） |
| **読込ボタン** | 追加取得量 | `readXxxPage(n)` で 1 チャンクずつ追加取得 |
| **表示リスト** | 画面上の件数 | 取得したチャンクを順に連結した配列だけを表示（従来の listToShowSlice は不要になる） |
| **更新時** | 取得タイミング | 更新の直前だけ `readXxxFull()` で全件取得してから `writeXxx()` |

この設計により、「読込スピード」は初回・追加読込ともに **1チャンク分のデータ量** にほぼ統一され、表示の「読み込み件数制限」は **チャンクサイズ（= 設定の初回読み込み件数）** で一貫した処理になる。

## 6. 実装済み（2026-02）

- **発注**: `orderApi.js` に v2 チャンク形式・`readOrderEntriesFirstPage` / `readOrderEntriesPage` / `readOrderEntriesFull`・移行・`writeOrderEntries` のチャンク書込を実装。`OrderHistoryList.jsx` を分割取得対応。
- **仕入**: `purchaseApi.js` に同様の v2 チャンク・FirstPage/Page/Full・移行・書込を実装。`PurchaseHistoryList.jsx` を分割取得対応（一覧はロケーションでフィルター）。
- **ロス**: `lossApi.js` に同様の v2 チャンク・FirstPage/Page/Full・移行・書込を実装。`LossHistoryList.jsx` を分割取得対応。
- **調整**: `adjustmentApi.js` に同様の v2 チャンク・FirstPage/Page/Full・移行・書込を実装。`AdjustmentHistoryList.jsx` を分割取得対応。
- **棚卸**: `stocktakeApi.js` に `readInventoryCountsFirstPage()` / `readInventoryCountsPage(i)` を追加。既存のバイト単位チャンクを1チャンクずつ取得。初回が単一キー（配列）の場合は `writeInventoryCounts` でバイトチャンク化してから先頭チャンクを返す。`InventoryCountConditions.jsx` を分割取得対応。
