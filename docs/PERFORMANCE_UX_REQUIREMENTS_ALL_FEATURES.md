# 全機能の読み込み・表示スピード体感改善 要件まとめ

**作成日**: 2026-02  
**目的**: 棚卸をはじめ、入庫・出庫・ロス・発注・仕入・調整・管理画面の**読み込みや表示の体感を早くする**ために、それぞれどのような要件にすればよいかを整理する。

行数（明細数）が最も多いのは**棚卸**だが、他タイルも「履歴一覧」「商品リスト」「検索リスト」など同様のパターンで負荷がかかるため、共通方針と機能別の要件を分けて記載する。

---

## 1. 体感を早くするための考え方

体感速度を改善するには、主に次の 3 つに分けて要件を決める。

| 観点 | 内容 | 例 |
|------|------|-----|
| **データ取得** | 何を・いつ・どの順で取るか。重複を減らし、並列化・遅延読み込みで「見えるまで」を短くする。 | 初回は軽い一覧だけ先に取得、詳細はタップ後に取得 |
| **表示（描画）** | 画面上に出す行数・DOM 数。多いとスクロールやタップの反応が鈍る。 | 仮想リストで「見えている範囲だけ」描画 |
| **操作フィードバック** | タップやスクロールへの即応答。処理は裏で続けても、UI は先に反応させる。 | タップ直後に画面遷移し、保存はバックグラウンド |

以下は、**現行実装から**これらを満たすために「要件をどうするか」の提案である。実装の難易度・影響範囲は機能ごとに異なる。

---

## 2. 共通要件（全機能で検討できるもの）

### 2.1 データ取得まわり

| 要件 | 内容 | 効果 |
|------|------|------|
| **初回は「一覧用」だけ先に取る** | 一覧に必要な項目（id, ステータス, 日付, 件数など）だけの軽い API/メタフィールドを用意し、初回表示はそれだけを読む。明細や groupItems は「詳細を開いたとき」に取得する。 | タイルを開いてから一覧が表示されるまでの時間を短縮。 |
| **並列取得** | 互いに依存しないリクエスト（例: 設定・商品グループ・1 チャンク）は `Promise.all` で同時に実行する。直列 4 本 → 1 回並列 + 1 回に減らす。 | ラウンドトリップの積み上がりを抑える。 |
| **同じデータの再取得をやめる** | 一度取った「商品グループ一覧」「設定」「ディスクリプタ」などを、同じ画面・セッション内ではオプションで渡し、API 内で再取得をスキップする。 | チャンクごと・ページごとの重複 GraphQL を削減。 |
| **ページネーション・追加読み込みの軽量化** | 「さらに読み込む」で次のページを取るとき、ディスクリプタやマスタを毎回取らない。前回取得したメタや cursor を渡して「追加分だけ」取る。 | 追加読み込みの待ち時間とタイムアウトを減らす。 |
| **タイムアウトの見直し** | 大規模データ（多数グループ・多数 SKU）では、追加読み込みや在庫取得のタイムアウトを 20 秒より長く（例: 60〜90 秒）し、途中で切れないようにする。 | 「追加読み込みに失敗しました timeout 20000ms」を防ぐ。（棚卸では既に 90 秒等に延長済み） |

### 2.2 表示（描画）まわり

| 要件 | 内容 | 効果 |
|------|------|------|
| **仮想リスト（ウィンドウ描画）** | 一覧・商品リストで「画面上に見えている範囲＋前後少し」だけ DOM を描画する。全行を一度に render しない。 | 行数が数百〜数千になってもスクロールやタップの反応が落ちにくい。棚卸が最も効果大。 |
| **初回表示件数の上限** | 設定の「初回読み込み件数」（例: 250）を守り、最初から全件取得しない。超過分は「さらに読み込む」で追加する。 | 初回の API 時間・パース・描画量を抑える。 |
| **スケルトン・読込中表示** | データが揃う前に「一覧の枠」や「読込中...」を先に出し、続けて中身を埋める。 | 体感として「すぐ反応した」と感じさせる。 |
| **画像の遅延読み込み** | 商品リストで画像を使う場合、表示域に入ったときだけ読み込む（lazy load）。 | 初回表示やスクロール時の負荷を減らす。 |

### 2.3 操作フィードバック

| 要件 | 内容 | 効果 |
|------|------|------|
| **タップ即応答** | 一覧で行をタップしたとき、**先に画面遷移（またはモーダル表示）**してから、詳細データ取得や保存処理を行う。重い処理は await でブロックしない。 | 「タップが効かない・遅い」を解消。（棚卸のグループ選択で実施済み） |
| **保存・更新はバックグラウンド** | ステータス更新やメタフィールド保存など、表示に必須でない処理は非同期（fire-and-forget）で実行する。 | 画面切り替えを待たせない。 |
| **ボタンの二重発火防止** | 読込中は「読込中...」表示＋ disabled にし、ref で二重送信を防ぐ。 | 意図しない重複リクエストを防ぎ、体感の「固まり」を減らす。 |

## 3. 機能別の要件

### 3.1 棚卸（行数・データ量が最大）

**現状**: 39 グループ・約 5600 SKU、商品リストは 250 件初回＋「さらに読み込む」600 件ずつ。一覧用 list メタ・チャンク並列・readInventoryCountsPage の軽量化・タイムアウト延長は一部実施済み。

| 要件 | 内容 | 優先度 |
|------|------|--------|
| **商品リストの仮想リスト化** | 棚卸の商品リスト（`InventoryCountList`）で、`lines` を全行一括描画せず、スクロール位置に応じて「見えている範囲＋バッファ」だけ描画する。POS のリストコンポーネントが仮想スクロールに対応しているか確認し、対応していなければ「表示行数の上限（例: 100 行）＋スクロールで追加描画」などの簡易版でも可。 | 高（行数が多いため体感改善が大きい） |
| **一覧の「名前」取得のキャッシュ** | ロケーション名・商品グループ名を、同一セッション内でキャッシュし、同じ id では再取得しない。既存の `product_group_names_v1` や `readProductGroupIds` を優先して使い、`readProductGroups()` の重複呼び出しを減らす。 | 中 |
| **readInventoryCountById の軽量化** | 棚卸 1 件取得時に「全チャンク結合」ではなく、**インデックス（countId → チャンク番号）** があれば該当チャンクだけ読む。既に `inventory_count_index_v1` の利用が進んでいれば、その徹底。 | 中 |
| **まとめて表示の「読込」負荷** | グループごと「読込」で `fetchProductsByGroups` ＋ 在庫取得（15 件バッチ）が重い場合、**初回は在庫なしで表示し、在庫はバックグラウンドで補填**するなどの段階表示を検討する。 | 中（要件変更がやや大きい） |
| **初回表示件数の設定遵守** | 商品リストの初回は `productList.initialLimit`（例: 250）を超えて取らない。追加は「さらに読み込む」のみ。 | 高（既存設定の徹底） |

### 3.2 入庫

**現状**: 履歴一覧（listInitialLimit）、商品候補（productList.initialLimit）、検索（searchList.initialLimit）の 3 項目を設定で反映。lineItems の pageInfo/after で追加読み込み対応。

| 要件 | 内容 | 優先度 |
|------|------|--------|
| **履歴一覧の初回軽量化** | 一覧に必要な項目だけを返す API／クエリにし、明細全件は詳細表示時だけ取得する。 | 中 |
| **商品リスト・検索リストの仮想リスト** | 候補リストや検索結果が数百件になる場合、仮想リストまたは「表示上限＋さらに読み込む」で描画量を抑える。 | 低〜中 |
| **タップ即応答** | 履歴行タップ時は先に詳細画面（またはモーダル）を出し、明細取得はそのあとでよい。 | 中 |

### 3.3 出庫（ModalOutbound）

**現状**: 履歴・lineItems・検索候補があり、商品リストは 250 件初回など。出庫明細が多くなると描画が重くなりうる。

| 要件 | 内容 | 優先度 |
|------|------|--------|
| **明細リストの仮想リスト** | 出庫明細（items/lines）が数百〜数千行になる場合、仮想リストで「見えている範囲だけ」描画する。 | 中 |
| **履歴一覧の軽量化** | 初回は id・ステータス・日付・件数程度にし、明細は詳細タップ後に取得。 | 中 |
| **検索・候補リスト** | 検索結果や候補が多くなったときの表示件数上限と、必要なら仮想リスト。 | 低 |

### 3.4 ロス

**現状**: 商品リスト（lines）、検索候補、履歴詳細。ロス明細が多くなると棚卸と同様に重くなりうる。

| 要件 | 内容 | 優先度 |
|------|------|--------|
| **商品リストの仮想リスト** | `LossProductList` で lines が多数のとき、仮想リストまたは表示行数上限で描画を抑える。 | 中 |
| **履歴詳細の「さらに読み込む」** | 詳細モーダルで entry.items を slice で表示し、超過分は「さらに読み込む」で 600 件ずつ増やす現行方式を維持。必要ならタイムアウトを延長。 | 低 |
| **検索・初回件数** | 検索リスト・商品リストの初回件数を設定どおりにし、重複取得を避ける。 | 中 |

### 3.5 発注・仕入

**現状**: 履歴一覧、発注/仕入明細（lines）、検索候補。`PurchaseHistoryList` などで detailDisplayLimit で 250 件初回＋600 件ずつ追加。

| 要件 | 内容 | 優先度 |
|------|------|--------|
| **明細リストの仮想リスト** | 発注・仕入の明細が数百件を超える場合、仮想リストで描画量を抑える。 | 中 |
| **履歴詳細の初回表示** | 詳細を開いたときの初回表示件数を設定（productList.initialLimit）に合わせ、追加は「さらに読み込む」のみ。 | 中 |
| **検索候補** | 検索結果の初回件数・追加読み込みのタイムアウトを他タイルと同様に揃える。 | 低 |

### 3.6 調整

**現状**: ロスと似た構成（商品リスト・検索・履歴詳細）。

| 要件 | 内容 | 優先度 |
|------|------|--------|
| **商品リストの仮想リスト** | `AdjustmentProductList` で lines が多数のとき、仮想リストまたは表示上限で描画を抑える。 | 中 |
| **履歴詳細・検索** | ロスと同様、詳細の「さらに読み込む」と検索の初回件数を設定どおりにし、必要ならタイムアウト延長。 | 低 |

### 3.7 管理画面（Remix）

**現状**: 棚卸は list メタ優先・チャンク並列・action でのフル取得限定を実施済み。履歴モーダルで数量編集・確定・キャンセル対応済み。

| 要件 | 内容 | 優先度 |
|------|------|--------|
| **一覧は list のみで完結** | 棚卸一覧は `inventory_counts_list_v1` があれば list のみで表示し、フルチャンクは読まない。list 未整備の過去データは従来どおりフォールバック。 | 高（実施済みの徹底） |
| **履歴モーダルは「必要時だけフル取得」** | モーダルで商品リストを表示するとき、list-only の場合は get_incomplete_group_products などで必要な 1 件分だけ取得。全チャンク結合は避ける。 | 高 |
| **テーブル・リストの仮想化** | 管理画面の履歴一覧やモーダル内の商品リストが長い場合、テーブルを仮想スクロール対応にするか、表示行数に上限を設ける。 | 中 |
| **loader の並列化** | 棚卸以外の管理画面ルートでも、複数 API を並列で呼び、直列の積み上がりを減らす。 | 低〜中 |

## 4. 実装の優先順位の提案

体感改善の効果と実装コストを踏まえた目安。

1. **すぐ効く（要件変更が小さい）**  
   - 全機能: **並列取得・重複取得の削減・タイムアウト延長**（未対応箇所のみ）。  
   - 棚卸: **初回表示件数と「さらに読み込む」の設定遵守**、**readInventoryCountById のインデックス利用の徹底**。  
   - 管理画面: **list 優先とモーダル時の必要時だけフル取得**の徹底。

2. **体感が大きく変わる（実装コストは中）**  
   - **棚卸の商品リストの仮想リスト化**（行数が最多のため最優先）。  
   - 出庫・入庫・ロス・発注・仕入・調整の**明細リストの仮想リスト化**（行数が多い画面から）。

3. **さらに速くする（要件・仕様の見直しあり）**  
   - 一覧用と詳細用の**データ構造の分離**（軽い一覧用メタ・API の整備）。  
   - **在庫の段階表示**（先に一覧を出し、在庫数はバックグラウンドで補填）。  
   - 自社 API で一覧/1 件取得を用意し、メタフィールドはキャッシュとして使う構成。

## 5. まとめ

| 観点 | 共通でやること | 棚卸で特にやること |
|------|----------------|-------------------|
| **データ取得** | 並列化、重複削減、初回は軽いデータだけ、追加読み込みの軽量化・タイムアウト延長 | 一覧は list のみ、1 件取得はインデックスでチャンク限定、商品リストは設定件数遵守 |
| **表示** | 仮想リスト（または表示上限）、スケルトン/読込中表示、画像の遅延読み込み | 商品リストの仮想リストを最優先 |
| **操作** | タップ即応答、保存はバックグラウンド、二重発火防止 | グループ選択タップ即遷移（済）、読込はバックグラウンド |

「今の実装から」体感を早くするには、**まず共通のデータ取得まわり（並列・重複削減・タイムアウト）と、棚卸の商品リストの仮想リスト化**を要件として押さえ、そのうえで他タイルの仮想リストや管理画面の仮想化を順に検討するのがよい。

既存の分析ドキュメント（`STOCKTAKE_APP_TILE_LOAD_PERFORMANCE_ANALYSIS.md`、`POS_STOCKTAKE_SLOWNESS_ANALYSIS.md`、`STOCKTAKE_UX_TAP_AND_LOAD_BUTTONS.md`）とあわせて参照すると、棚卸まわりの現状と実施済み対策が分かる。
